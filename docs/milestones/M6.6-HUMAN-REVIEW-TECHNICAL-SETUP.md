# M6.6 Human Review: Database and Pages

## Database

The M6.6 review path is additive. `V20261107170000__add_benchmark_catalogue_and_review_v2.sql`
creates versioned benchmark and review tables while retaining the legacy
`review_batches`, `review_cases`, `review_assignments`, `reviews`,
`adjudications`, and `review_audit_events` tables.

The `b_mst_` tables hold dataset versions, immutable case snapshots, review
categories, category labels, benchmark dimensions, and AI-generated reference
proposals. Catalogue registration
hashes the complete dataset and each case. Re-registering identical content is
idempotent; changing content under an existing dataset version is rejected.
Imported labels remain marked draft/provisional until separately reviewed and
approved.

The `b_review_` tables hold batches, cases, assignments, audit events, and
reference proposals. `b_reviews` distinguishes `BLIND`, `PROPOSAL_ASSISTED`,
and `POST_AI` opinions. A proposal-assisted opinion stores the exact
`reference_proposal_id`; it is not counted as blind. A post-AI opinion must
reference a successful `reliability_attempts.id` for the same dataset version
and case. `b_human_ai_comparisons` preserves the exact case version, blind
opinion, optional post-AI opinion, and AI attempt used for comparison.

`mst_ai_models` is shared by reliability experiments and attempts. The
migration backfills existing model identifiers and adds nullable model
references, preserving historical records. Existing review workflow rows are
copied into the new tables; legacy tables are not dropped.

## Pages and API

- **Reviewer page:** `/evaluate/cases/:caseId` loads the assigned batch and
  case. Where an AI-generated reference proposal exists, it is labeled as a
  proposal, shown separately from the review form, and can be copied into an
  editable rationale draft. **Submit review** below each case saves an editable
  entry and moves to the next unsaved case (or the dashboard after the last case).
  There is no primary final-review preview or finalization on an individual case.
  Saved entries count toward the reviewer's dashboard coverage, but not finalized
  case/batch completion or adjudication. Existing reviews created before this flow are migrated as
  editable drafts, except reviews belonging to already-adjudicated cases.
  Post-AI opinions use the same editable-preview-final-submit flow and remain
  tied to an exact persisted AI attempt. Submissions reference the proposal and are recorded as
  `PROPOSAL_ASSISTED`, not blind. Without a proposal, the blind workflow
  remains unchanged.
- **Review home:** `/evaluate` shows **Submit final review** only when every case
  assigned to the current reviewer has a saved primary entry. It opens
  `/evaluate/final-review`, displaying all saved labels, rationales, review stages,
  optional notes/findings, and case context. **Edit review** opens that case and
  returns to a freshly loaded preview after saving. Only **Confirm and submit
  final review** finalizes all the reviewer's primary entries together, atomically.
  Other reviewers' entries are not finalized. A changed preview is rejected
  until reloaded; a final submission locks those entries. Already-final entries
  remain read-only. This uses the existing `is_final` column; no additional
  database migration is needed.
- **Adjudication page:** the admin page lists explicit disagreements, shows the
  two primary-review rationales, identifies each review stage, and offers only
  labels allowed by that case's category.
- **Progress:** the admin page reports review completion and AI evaluation
  coverage by category. Blind and proposal-assisted reviews determine
  agreement, disagreement, adjudication, and batch completion; their distinct
  stages remain available for analysis.
- **API:** `/api/v1/human-review` registers catalogue versions when a batch is
  created, serves reviewer queues, case context, and eligible reference
  proposals, saves editable primary entries at `POST .../reviews` (and retains
  `PUT .../reviews/draft`), serves the reviewer-only snapshot at
  `GET /batches/{batch_id}/reviews/preview`, and finalizes all assigned primary
  entries at `POST /batches/{batch_id}/reviews/final` using the preview token.
  Missing cases or changed snapshots return a conflict without partial
  finalization. Batch row locking serializes saves and finalization.
  Post-AI opinions retain their separate per-case final submission after primary
  batch confirmation. The API accepts blind, proposal-assisted, and post-AI reviews, and
  exposes adjudication, progress, and audit endpoints. `b_reviews.is_final`
  distinguishes editable drafts from immutable submissions; draft edits and
  previous values are recorded in the review audit log.

## Rollout

On 8 November 2026, at the owner's explicit request to keep the current
dataset version, 38 missing goal titles were added to the active unapproved
v3 draft and the 52-case JSON export. Existing goals, case questions,
evidence, labels, proposal rationales, assignments, and saved review entries
were preserved. Intentionally vague goals remain vague. The local catalogue
snapshots and content hashes were synchronized with an audit trail after
checking that no finalized reviews or executed AI attempts depended on them.
This is a one-time draft-data correction, not permission to rewrite reviewed
or evaluated case versions. The added synthetic context still requires human
validation; saved reviews on affected cases should be rechecked before final
submission. Batch preview tokens include case-content hashes so context
changes also require a fresh preview.

Apply the additive migrations before deploying the new API. Create a review
batch from an exact dataset ID/version; dataset labels and thresholds remain
unapproved until human review and the approval workflow are complete. Verify
the new workflow and historical backfill before considering any legacy-table
retirement. No legacy tables are removed by this implementation.
