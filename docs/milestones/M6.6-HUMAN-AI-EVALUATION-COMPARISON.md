# Human–AI Evaluation Comparison

**Dataset:** `m66-intelligence-comparison-v1`  
**Prompt version:** `m66-category-assessment-v1`  
**Model:** `openai/gpt-oss-20b` through Groq  
**Review mode:** `SINGLE_REVIEWER`  
**Document status:** Exploratory development evaluation  
**Evaluation date:** 1 November 2026

## Purpose

This evaluation compares MyImpact's structured AI assessment output with
human-reviewed expectations across goal, evidence, and explanation categories.
It is intended to identify model behavior, repeatability, evidence-selection
stability, and citation stability. It is not a release approval or a substitute
for human review of the benchmark dataset.

## Expanded benchmark implementation

The follow-up benchmark is available as
`m66-intelligence-comparison-v2` in
`evaluation/m66_intelligence_comparison_v2.json`. It preserves the
14-case baseline and adds 20 cases for a total of 34. The draft cases
include category-specific human labels and AI mappings, role context,
evaluation periods, and robustness dimensions. Citation grounding uses
`UNGROUNDED` as the provisional negative label.

The expanded dataset is intentionally marked `DRAFT_UNREVIEWED`, uses
`DUAL_ADJUDICATED` review metadata, and keeps threshold approval at
`NOT_APPROVED`. It is ready to be reviewed and run as a separate
experiment, but its results must not be presented as release approval.

## Dataset scope

The comparison dataset contains fourteen cases, each evaluated three times:

- Valid goal
- SMART goal quality
- Duration achievability
- Criterion clarity
- Time validity
- Quantitative measurement
- Citation grounding
- Abstention
- Outcome classification
- Evidence relevance
- Evidence sufficiency
- Contradiction handling
- Attribution

The dataset includes direct support, partial progress, contradictory evidence,
irrelevant semantic matches, missing evidence, attribution boundaries,
quantitative evidence, time validity, and citation-grounding scenarios.

The dataset is currently marked:

```text
label_status: DRAFT_UNREVIEWED
human_review.status: PENDING
threshold_approval.status: NOT_APPROVED
```

## Questions and scenarios

Each case presents the same goal, criterion, and evidence context to the
evaluation workflow. The human reviewer answers the category-specific
question using the allowed review labels. The AI assessment answers the
corresponding structured assessment question and selects supporting,
contradictory, or insufficient evidence. The expected decision below is the
current dataset reference label; it remains provisional until human review is
completed.

| Category | Assessment question | Scenario presented | Expected reference decision |
|---|---|---|---|
| Outcome classification | Does the evidence show that production canary validation was enabled and verified? | Direct evidence satisfies the completion condition, but unrelated planning evidence is also present. | `MET` |
| Outcome classification | Is production canary validation complete for all production services? | Evidence shows meaningful but incomplete progress toward the completion condition. | `IN_PROGRESS` |
| Contradiction handling | Can the system determine whether production release failures were reduced? | Relevant sources conflict, so both sources should be cited and a definitive outcome avoided. | `NEEDS_REVIEW` |
| Evidence relevance | Does the evidence support enabling production canary validation? | The text is topically similar but does not provide evidence for the criterion. | `NEEDS_REVIEW` |
| Evidence sufficiency | Does the evidence show progress on reducing service incidents? | No evidence was retrieved or submitted; missing evidence is not proof of no progress. | `NEEDS_REVIEW` |
| Attribution | Did the employee lead the implementation of production canary validation? | A positive team outcome is documented, but the employee's contribution is not established. | `NEEDS_REVIEW` |
| Valid goal | Is the customer support improvement goal concrete, relevant, and connected to a meaningful outcome? | The goal is concrete, relevant, and connected to a meaningful work outcome. | `MET` |
| SMART goal | Is the goal SMART? | The goal includes a clear measure, target, owner, and deadline. | `MET` |
| Duration achievability | Is the goal achievable within the stated duration? | The requested result is much larger than the available time and resources. | `NEEDS_REVIEW` |
| Criterion clarity | Is the success criterion clear and measurable? | The goal uses an ambiguous success phrase without defining how success will be measured. | `NOT_ASSESSED` |
| Time validity | Is the evidence current for the evaluation period? | The evidence describes an old result outside the evaluation period. | `NEEDS_REVIEW` |
| Quantitative measurement | Does the evidence support the stated numeric target? | The evidence claims improvement but does not support the stated numeric target. | `NEEDS_REVIEW` |
| Citation grounding | Does the explanation cite evidence that supports its conclusion? | The explanation cites evidence that does not support the stated conclusion. | `MET` |
| Abstention | Can the system determine whether onboarding completion improved? | The available information is too incomplete to decide whether the goal was met. | `NOT_ASSESSED` |

For human review, the answer options are category-specific. Examples include
`MET`, `IN_PROGRESS`, and `NEEDS_REVIEW` for outcome cases; `VALID` and
`INVALID` for goal validity; `SMART` and `NOT_SMART` for SMART quality; and
`GROUNDED`, `UNGROUNDED`, or `NEEDS_REVIEW` for citation grounding.

For AI assessment, the same scenarios are evaluated through structured
criterion assessment. The comparison checks the predicted assessment label,
evidence selections, contradiction handling, citations, abstention decision,
and rationale support rather than comparing free-form text alone.

## Method

The reliability experiment used:

- 14 required cases.
- 3 repetitions per case.
- 42 planned attempts.
- The production structured assessment prompt.
- Structured JSON output validation.
- Evidence and citation validation.
- Normalized comparison of assessment labels, evidence selections,
  contradictions, citations, abstention decisions, and exact outputs.

Groq-only request pacing was enabled to avoid the provider's 8,000-token-per-
minute limit. The earlier category-aware run completed only 6 of 42 attempts
because of Groq rate-limit failures. The retry was run after the pacing change.

## Completed retry

| Measure | Result |
|---|---:|
| Planned attempts | 42 |
| Completed attempts | 42 |
| Run success rate | 100.0% |
| Structured output validity | 100.0% |
| Label consistency | 92.9% |
| Evidence selection consistency | 85.7% |
| Citation set consistency | 85.7% |

All fourteen case comparisons completed. The retry did not reproduce the
earlier rate-limit failures.

## Observations

### Stable behavior

The model was highly stable for:

- Valid-goal classification.
- Abstention decisions.
- Citation-grounding scenarios.
- Cases with direct and unambiguous evidence.

### Variable behavior

The following cases showed model-output variation across repetitions:

- Partial canary rollout.
- Semantic match without relevance.
- Team outcome without individual attribution.
- Duration achievability.
- Quantitative measurement.
- Time validity.

The partial-rollout case is particularly important because the output varied
between `IN_PROGRESS` and `NEEDS_REVIEW`. This case requires human review of
the wording, completion conditions, evidence interpretation, and expected
label before any quality threshold is proposed.

## Interpretation

The retry demonstrates that:

1. The reliability workflow can execute the complete category-aware benchmark.
2. Groq request pacing prevents the earlier provider rate-limit failures.
3. Structured output and citation validation are functioning for the completed
   run.
4. The model is not fully repeatable on all ambiguous or attribution-sensitive
   cases.
5. Consistency must be evaluated separately from correctness; a consistent
   answer is not automatically a valid answer.

The `57.1%` repeatability result is exploratory. It must not be interpreted as
a release pass or fail until the reference labels are reviewed and numeric
thresholds are approved.

## Limitations and governance

- The dataset is not yet human-reviewed ground truth.
- The comparison uses one reviewer per case by design; it is not the
  two-reviewer adjudicated release dataset.
- No approved model version is recorded.
- No numeric threshold set has been approved.
- The current benchmark is small and should be expanded with additional
  temporal, stale-evidence, measurement, attribution, and mixed-relevance
  cases.
- The unsupported-claim metric is an outcome-level proxy and does not verify
  every factual statement in an AI rationale.
- The run validates development behavior, not production deployment behavior.

## Conclusion

The human–AI comparison retry is **complete for exploratory development
evaluation**: all 42 attempts succeeded, structured outputs were valid, and
the comparison report was generated.

It is **not release evidence**. Human review, dataset approval, threshold
approval, and integrated release validation remain required before the results
can support a production go/no-go decision.
