# M5.6 — Chat API

## Goal

Expose a product-facing `/api/v1/chat` endpoint while keeping the existing LLM implementation behind the API boundary.

## API

`POST /api/v1/chat?user_id={user_id}`

Request:

```json
{
  "message": "How should I prepare for my 1:1?"
}
```

Response:

```json
{
  "message": "..."
}
```

## Design

```text
Product Chat Request
        ↓
/api/v1/chat
        ↓
ChatService
        ↓
ILLMService
        ↓
Groq / Azure
```

- Reuses the existing `ILLMService` abstraction and provider factory.
- Keeps the provider/model name out of the product response.
- Requires `user_id` at the API boundary until authentication is introduced.
- The current milestone is stateless: no chat history or new database tables.
- Does not expose LLM prompts, provider configuration, or implementation details.
- Empty/whitespace messages are rejected.
- Existing legacy `/chat` endpoint remains unchanged.

## Files

- `app/models/api_v1_chat.py` — product request/response contracts
- `app/services/chat.py` — thin chat orchestration service
- `app/api/v1/chat.py` — product-facing endpoint
- `app/api/v1/router.py` — register Chat API
- `tests/unit/api/v1/test_chat.py` — focused Chat API tests

## Boundary

M5.6 establishes the product Chat API only. Persistent conversation history, authenticated user context, knowledge retrieval, goal-aware context, and assistant orchestration are intentionally not added here.
