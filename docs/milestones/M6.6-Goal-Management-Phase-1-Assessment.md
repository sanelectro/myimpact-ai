## 1. Executive decision

Extend the existing product backend and domain services. Do not introduce a second Goal model, hierarchy system, evidence engine, version-history system, or multi-agent platform.

The current code already supports all four Goal Levels, persisted same-owner parent relationships, cycle prevention, relationship revision checks and audit events, goal versions, version-specific approval, evidence archival, PDF/DOCX extraction, and a substantial M6.6 evaluation/reviewer foundation.

It does **not** implement the requested document-driven Goal Change Plan workflow or the agreed version vault. Existing document import creates flat Draft goals immediately; it neither reconciles changes nor provides selective pre-application review. Parent-specific decomposition, descendant change analysis, proposal concurrency/idempotency, version-isolated lifecycle/evidence references, and Jira REST planning retrieval remain gaps. Jira MCP is deferred and is not a blocker for the current scope.

The most important corrections to a greenfield design are:

1. Reuse `goal_level`, `parent_goal_id`, `relationship_revision`, and `goal_relationship_events`; they are implemented, not just proposed.
2. Reuse `documents.content_hash`, processing status, file storage, and heading-aware chunks. A second document table or fingerprint column is unnecessary.
3. Reuse evidence archival and existing many-to-many mappings. Relationship retirement is missing, but evidence archival itself is not.
4. Reuse immutable version content, validation and approval, but extend lifecycle and retrieval into a version vault. Existing snapshots alone cannot keep an operative version untouched while its replacement is Draft.
5. Keep existing criterion assessment behavior backward compatible, but do not invoke its progress/achievement calculations from the new planning agent.
6. Keep Jira REST-based for now. Extend authorized read-only retrieval for planning rather than changing the existing completed-work evidence-discovery behavior. MCP is deferred, not a current acceptance requirement.

**Recommendation:** Finalize the bounded Phase 2 foundation design against the confirmed policies, verify the migration/test baseline, and wait for explicit implementation approval. Do not declare the expanded M6.6 complete.

### Confirmed product decisions: 10 November 2026

These decisions supersede the earlier alternatives in this assessment and the original mandatory-MCP requirement. They approve product behavior, not coding or migration execution.

| Area | Confirmed behavior |
|---|---|
| Version vault | A new logical goal starts at v1. Editing creates a new Draft version without changing the prior version's definition or operative behavior. A replacement must be explicitly approved and activated before it takes over. |
| Activation handover | Activating approved v2 atomically deactivates v1. Approval alone does not deactivate the operative version. At most one version per logical goal/version family can be Active, including under concurrent requests. |
| Older versions | Historical/superseded versions cannot be reactivated. Their evidence remains available for reference in newer versions; history is not deleted. |
| Similar independent goals | Similar separately created goals are flagged for duplicate review, not automatically treated as members of the same version family or blocked solely for sharing a Goal Level/context. |
| Employee ownership | Every goal and version belongs to that employee, including team- and organization-scoped goals. Scope is not delegated/shared ownership. |
| Evidence carry-forward | The employee selects approved evidence references to include in the replacement version. Reuse the evidence record; retain links to the older version. Carried approval retains its original provenance and does not approve the goal version. |
| Evidence retirement | At handover, old-version relationships become inactive for current use but remain historical. Unselected evidence is not added to v2 and is not globally deactivated. Evidence and its relationships to other goals remain unaffected; historical evidence can be referenced again without reactivating the older goal. |
| Atomicity | Every explicitly selected dependency-complete apply batch and every activation handover is all-or-nothing. Any failure rolls back all domain changes in that process. |
| Hierarchy | Children remain attached to the logical parent goal when its operative version changes. Evaluate affected children and review necessary changes separately; do not copy, reschedule or require blanket reapproval of every child automatically. |
| Date conflicts | Block applying a child change outside its parent's timeframe until dates or parent relationship are resolved. No acknowledged-exception bypass and no automatic parent rescheduling. Activation must also preserve a consistent operative hierarchy. |
| Jira | Use existing Jira REST integration as the foundation and extend planning retrieval as needed. MCP implementation/configuration/live validation is deferred and is not a current blocker. |

### Existing document-to-goal workflow

1. User uploads through the reusable document UI.
2. The backend stores the original bytes and SHA-256 hash, extracts Markdown, classifies the document, and can persist expectations and chunks.
3. The Goals import page calls `POST /api/v1/goals/import-from-document`.
4. Import reads the processed Markdown and asks the configured LLM for a flat candidate list.
5. It returns already imported goals for the same document ID; otherwise it applies deterministic text-duplicate checks.
6. Each nonduplicate candidate is immediately persisted as a Draft, with source document ID.
7. The UI offers review/edit of those already-created drafts, not accept/reject of a pending change plan.

Sources: [document upload](../../app/services/document.py#L82), [goal import](../../app/services/goal_import.py#L39), [import contract](../../app/models/goal_import.py#L8), [import endpoint](../../app/api/v1/goal_import.py#L26), and [import UI](../../../myimpact-web/src/pages/Goals/GoalImportPage.tsx#L9).

### Proposed workflow

```text
Upload/process document using existing ingestion
  -> identify authorized employee planning context and canonical document hash
  -> gather existing goals/versions, hierarchy, prior sources, evidence relationships
  -> retrieve authorized read-only Jira REST planning context when relevant
  -> extract source-grounded facts and candidate commitments
  -> compare and decompose independently under each identified parent
  -> persist a versioned Goal Change Plan, not live goal mutations
  -> deterministic validation + explicit uncertainty/clarification
  -> employee reviews original/proposed values, sources and consequences
  -> selected accept/reject/edit decisions are recorded
  -> explicit apply rechecks ownership, versions, relationships and dependencies
  -> existing domain services stage permitted confirmed changes as Draft versions
  -> version-specific validation and explicit approval remain separate
  -> explicit activation atomically switches the operative version and evidence references
```

Only goal-related ingestion should trigger this workflow. Do not automatically turn role expectations, personal evidence uploads, or every knowledge reprocess into goal writes.

## 5. Lifecycle, history and compatibility findings

### Goals and approval

- New v1 creation and file import create Draft goals.
- Approval/activation normally require a persisted READY run for the latest version; activation requires version approval. Legacy versions can be exempt under the existing setting.
- Archival requires a nonblank reason. Archived goals have no ordinary outbound lifecycle transition.
- Material edits create a new USER-origin version. Editing a legacy goal can therefore change its eligibility behavior.
- Existing update allows material changes while status remains Active or Approved; the new version is not automatically approved. Evidence submission becomes ineligible until current-version gates are met.
- Existing parent mutations are separate from definition approval and are permitted through the owner-checked hierarchy service without changing goal status.

**Confirmed design change:** Preserve the existing version content and audit mechanisms, but implement an operative-versus-Draft version vault. The current mutable Goal/latest-snapshot behavior does not satisfy this policy. Neither acceptance nor a plan apply call may invoke approval/activation automatically.

The logical goal is the stable version-family identity. Its operative version remains unchanged and eligible under its own validation/approval while a replacement Draft is edited or approved. Draft, approved and operative views must select the intended version explicitly rather than treating the latest snapshot as universally authoritative.

Explicit activation of the approved replacement must atomically deactivate the previous operative version and activate the replacement. Enforce at most one Active version per family in persistence as well as application validation. Never use text similarity or equal Goal Level as the active-version uniqueness key. Older superseded versions are immutable historical versions and cannot be reactivated; evidence may be referenced into newer versions without restoring the older goal.

Children stay attached to the stable logical parent. Historical views retain the parent/version context that applied at the time. A new parent version triggers targeted descendant impact analysis, not automatic child copying or mandatory review of every unaffected child. A prospective out-of-parent date conflict blocks the affected change/activation until dates or relationships are resolved.

Goal snapshots include level, definition, source and criteria; parent history belongs to relationship events. Reuse these stores and retain version context in lifecycle, proposal/application and relationship events. Criteria and assessment inputs must resolve against the selected version rather than accidentally showing the latest Draft under the active version.

### Evidence and relationships

- Evidence lifecycle includes Active, Archived and Deleted; ordinary archive uses the existing Archived state.
- Mapping approval is a separate employee/manager workflow. Creating a mapping creates a pending approval through [EvidenceMappingService](../../app/services/evidence_mapping.py#L20).
- Mapping has no archival timestamp or independent current/inactive relationship state.
- Inherited visibility is contextual and must not become an automatically approved mapping or proof of parent achievement.
- Existing explicit permanent deletion is separate from archival. The agent's tool allowlist must not include goal/evidence deletion.

**Confirmed carry-forward behavior:** Before replacement activation, show the employee the approved evidence references available from older versions and record their explicit selection. Selected references point to the existing evidence record in v2 and retain original approval/source provenance. Do not create duplicate evidence or fabricate a new manager approval decision. Carrying evidence does not approve v2 or prove its achievement.

During the atomic handover, retain all v1 links for historical viewing while making them inactive for current v1 use. Activate only the selected v2 references; unselected evidence remains available in history for later reference into a newer version. References staged for a Draft must not appear as operative evidence before activation.

For evidence shared by Goals A and B, deactivating A/v1 must leave the evidence and B's mapping intact. Retirement applies to the goal-version relationship, never to the shared evidence record merely because it was not selected. Global evidence archival remains a separately explained and confirmed action for actual obsolescence/invalidation/supersession, not part of routine version handover.

### Scope conflicts to keep explicit

The historical [M6.6 brief](M6.6-README.md#evidence-assessment) includes criterion completion and deterministic progress. New Goal Management must not silently change those existing APIs/UI or relabel historical evaluations as planning evaluations. Likewise, existing [goal measures](../../app/api/v1/goal_measures.py#L25) distinguish child execution counts from undetermined outcome/impact. Keep that distinction.

## 6. Proposed Goal Management Agent and services

Implement one application-level orchestrator in `myimpact-ai`, using ordinary reusable services. It reasons and coordinates; domain services remain responsible for writes.

| Responsibility | Reuse/extension |
|---|---|
| Extract document facts/goals | Existing storage, Docling, classification, chunks and LLM interface; extend import extraction into a source-grounded candidate service without immediate persistence. |
| Read planning context | Owner-scoped GoalRepository, existing hierarchy/context services, versions, criteria, evidence/mappings and prior document references. Add bounded descendant traversal and explicit completeness metadata. |
| Retrieve Jira planning context | Extend existing read-only REST integration into a typed, sanitized planning snapshot and retrieval outcome. No MCP dependency or general autonomous tool executor in current scope. |
| Generate/reconcile | Structured LLM proposal per parent and requested child level, followed by deterministic matching and cross-operation validation. |
| Validate plans | Extend/reuse existing goal validators; add source checks, operation allowlist, concurrency, hierarchy overlay, evidence and dependency checks. This must not rely on LLM confidence. |
| Review and apply | Dedicated plan service records decisions; apply coordinator stages Draft version changes through existing services under a shared transaction. A separate explicit version-activation action performs atomic operative/evidence handover. |

### Deterministic orchestration

1. Resolve the token-bound actor; load only authorized documents and goals. Do not trust model-supplied owner or database identifiers.
2. Claim a durable content-hash/idempotency record, snapshot context and release database transactions before LLM/REST calls.
3. Extract goals, objectives, activities, deliverables, responsibilities, expectations and background separately. Non-goals may inform context but must not automatically become goals.
4. Match candidate commitments against logical goal families and their Draft/Approved/Active/Completed/inactive historical versions. Conflicting numeric targets are a potential replacement version, not proof of a new logical goal.
5. Resolve explicit parent references before decomposition. For each Quarterly parent independently request Monthly children; repeat independently for each Monthly parent and Sprint children, with relevant Jira context.
6. Candidate nodes use stable plan-local IDs and explicit parent references. Allow zero children, standalone nodes, supported skipped levels and multiple roots; reject unknown/cyclic/cross-owner links.
7. Analyse only the changed parent's descendant branch plus explicitly identified dependencies. Existing `dependencies` are free-text strings, not a persisted graph: unresolved references become clarification, not guessed edges.
8. Validate the complete proposed graph after applying operations in memory, including mixed ADD/REPARENT/RESCHEDULE operations. Do not validate each operation against only the original graph.
9. Persist source-grounded output and issues; show blocked/clarification proposals with errors, not an apparently valid plan.
10. Apply only explicitly selected and permitted operations after fresh deterministic checks, with all selected writes rolling back on any failure. Definition changes create Draft versions without replacing the operative version. Retain the original AI payload, employee edits, decisions and resulting identifiers.

Bound document/context size and provider calls; expose truncation and partial retrieval. Do not treat omitted context as evidence that no matching goal or dependency exists. No LLM/network call belongs inside the hierarchy lock or apply transaction.

### Parent-specific postponement case

For November timezone validation moving to December and December timestamp validation moving to January:

- Propose separate Draft reschedule versions of the matched Monthly goals, preserving their logical identities and parent links.
- Inspect only their Sprint descendants and explicit dependencies; retrieve relevant Sprint context through REST.
- Propose Sprint changes only when supported; show unchanged descendants and why.
- Flag January work outside the existing Q4 deadline as a blocking parent/child scheduling conflict. Do not apply it until dates or parent relationship are resolved.
- Preserve the Quarterly deadline unless an explicit source/employee decision justifies changing it; request clarification instead of mechanically shifting it.
- Do not touch sibling Quarterly branches merely because their dates overlap.

## 7. Goal Change Plan contract proposal

Names and endpoints here are proposed, not implemented.

### Plan and operation shape

```text
GoalChangePlan
  id, schema_version, revision, actor_user_id, document_id, document_content_hash
  request_idempotency_key, evaluation_generation, reprocess_of_plan_id
  status, created_at, updated_at, prompt_version, model_provider, model_version
  context_snapshot: goal families, operative/draft version IDs, relationship revisions, source snapshots
  jira_retrieval: outcome, fetched_at, coverage, errors, source references
  operations[], validation_issues[], clarification_requests[]

GoalChangeOperation
  id, operation: ADD | UPDATE | RESCHEDULE | REPARENT | ARCHIVE
                 | SUPERSEDE | NO_CHANGE | NEEDS_CLARIFICATION
  target_goal_id?, target_goal_version_id?, proposed_goal_ref?
  parent_goal_id? | parent_operation_ref?
  expected_active_goal_version_id?, expected_latest_goal_version_id?
  expected_relationship_revision?
  original_values, original_ai_proposal, edited_proposal?, changed_fields[]
  rationale, parent_contribution_rationale?, confidence?, missing_information[]
  source_references[], affected_descendants[], evidence_impacts[]
  selected_source_mapping_ids[], approval_provenance_references[]
  depends_on_operation_ids[], validation_issues[]
  decision, decision_actor?, decision_at?, applied_result?

SourceReference
  document_id?, document_hash?, extracted_content_hash?, extraction_version?
  page?, section?, paragraph_or_span?, exact_quote?
  jira_site_id?, issue_key?, issue_url?, sprint_id?, source_updated_at?, fetched_at?
```

Reuse existing Goal Level, scope and evidence enums and extend existing version/lifecycle mechanisms only where required for the vault. Each persisted goal family/version is owned by the authenticated employee, including team/organization scopes. An extracted external owner is source context, not a delegated MyImpact owner; unresolved ownership attribution requires clarification rather than silently assigning someone else's commitment. Candidate level may remain unspecified.

Source references should snapshot quotes/anchors. Existing normalized Markdown and section paths can support sections/spans; the adapter currently discards Docling's structured page provenance. Extend extraction metadata when available and never invent page numbers. Existing expectation page/section columns do not provide citations for extracted goals.

### Operation semantics

| Operation | Effect after valid explicit confirmation |
|---|---|
| ADD | Create a logical goal with Draft v1 through GoalService; persist employee ownership, explicit resolved parent and source metadata. Never set approved/active/completed. |
| UPDATE | Create a replacement Draft version with only the reviewed definition changes; leave the operative and historical versions untouched. Criteria changes reuse existing criteria-versioning and retain version-specific visibility. |
| RESCHEDULE | Create a Draft date revision with old/new dates, reason and descendant impact. No mechanical parent-date changes; out-of-parent dates block application until dates/relationship are resolved. |
| REPARENT | Reuse hierarchy validation, revision checks and event history, extended with vault context. Stage any relationship change that would affect an operative version until explicit activation; retain historical parent context and logical child identity. |
| ARCHIVE | Invoke existing reason-required archival transition with separate confirmation and evidence impact review. No physical deletion. |
| SUPERSEDE | A replacement of the same commitment stays in the same logical family and starts as a new Draft. Keep the prior operative version until explicit activation of the approved replacement; then deactivate it atomically, retaining history. A distinct commitment is a separate family, not an implicit version or automatic archival trigger. |
| NO_CHANGE | Retain reasoning and sources; never write a new goal/version merely to record no change. |
| NEEDS_CLARIFICATION | Retain questions/issues; cannot be accepted/applied as a mutation until corrected and revalidated. |

Evidence impacts are separately identified review items: preserve, carry an approved reference to a new version, retire one version-specific mapping, or archive evidence itself. They need individual IDs and explicit decisions. Carry-forward retains the original approval provenance. Selecting goal archival or replacement activation must not implicitly archive the evidence record.

| `POST /goal-change-plans` | `{document_id, intent, requested_levels?, parent_goal_ids?, reprocess_of_plan_id?}` plus `Idempotency-Key`. Creates a bounded evaluation, not goals. Returns plan/processing outcome; same request key returns the same resource. |

Proposed failures: 401/403 authentication/authorization, owner-safe 404, 409 stale plan/goal/relationship/idempotency conflict, 422 invalid plan/selection, and explicit categorized 502/503 provider failures. Persist sanitized failure history; do not return an empty successful plan for a failed extraction or inaccessible Jira source.

Initially use bounded request execution rather than introducing a queue. Define timeout/retry recovery for persisted RUNNING records. A durable asynchronous worker is a later measured need, not part of this proposal by default.

### Idempotency and employee-edit protection

- Reuse raw document SHA-256; deduplicate evaluation/application, not necessarily every upload record.
- A normal evaluation is uniquely claimed by owner, document hash, workflow version and generation zero. An explicit reprocess allocates a new generation under a lock and references the previous plan.
- Each request key is unique per owner and stores an input digest; reusing it for different input is a conflict. Concurrent identical requests converge on the same plan.
- Re-uploading identical bytes returns the prior plan, including NO_CHANGE/empty results. An outdated plan is labelled stale; ask for explicit reprocessing instead of silently regenerating.
- A revised document has a different hash, but still compares against existing commitments. Matching uses source identity, meaning, level, owner, parent and timeframe; text similarity alone is not authoritative.
- At apply/activation, lock logical goal families in a stable order and compare captured operative/latest/target version IDs, relationship revisions, and affected evidence/mapping/approval snapshots. Any mismatch requires re-review/reprocessing; never overwrite employee edits or switch from a stale operative version.
- Reprocessing creates a new proposal history, not edits to previously accepted/manual content. Preserve rejected decisions and allow deliberate re-review with provenance.
- An applied operation has one immutable apply result. A repeated apply returns that result, not another version, goal or mapping.
- ADD matching and uniqueness checks must run again inside the apply concurrency boundary. Prevent simultaneous plans from creating the same accepted source commitment.
- Concurrent activation requests must converge on at most one operative version per logical family; enforce this in database constraints as well as locked application checks. A historical superseded version is not a valid activation retry target.
