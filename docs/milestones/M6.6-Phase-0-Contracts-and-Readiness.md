## 3. Domain vocabulary and materiality

| Term | Meaning |
|---|---|
| Goal | Stable employee-owned business identity, not a particular target snapshot |
| Definition version | Immutable complete meaning: Goal fields, selected criterion/milestone definitions and relevant source context |
| Operative version | Explicitly selected definition used for current reads and execution; not inferred from maximum version number |
| Proposal | Editable/reviewable candidate context that does not alter current execution |
| Publication | Explicit selection of an eligible validated ongoing definition, preserving Goal ID and lifecycle |
| Lifecycle | Existing Draft/Approved/Active/Completed/Archived state |
| Disposition | Read-only/execution eligibility reason, such as descoped or continued; not a new lifecycle status |
| Planning context | Current eligible parent/version/date association, distinct from historical execution and completed commitments |
| Historical contribution | Work attributable to its original context; not automatic credit against revised commitments |

### Definition-change classification

Versioned semantic fields include meaningful title/description edits, scope/organization context, Goal level, planned dates, outcomes, baseline/target/units, deliverables, accountability, success criteria, milestone definitions, dependencies, deferrals and source commitments.

- Exact no-op: return an explicit no-change result; do not allocate another version or invalidate review.
- Whitespace-only correction: no semantic publication. Preserve content where whitespace carries formatting meaning; canonicalization must not alter Markdown structure, quoted source or code-like text. If normalization cannot prove equivalence, treat the edit as semantic.
- Semantic edit to an ongoing commitment: prepare, validate, explicitly publish.
- Material new commitment for a Completed Goal: replacement workflow, not in-place publication.
- Criterion/milestone definition changes follow the same protected definition boundary.
- Milestone completion/progress, evidence submission and ordinary lifecycle transitions are execution commands, not automatic definition publications.
- Parent relationship changes require explicit structural/context validation and audit; they cannot be hidden inside a whitespace correction.

Do not silently edit an immutable version for presentation cleanup. A no-op normalization may be ignored or rendered canonically without changing the historical stored commitment.

Draft preparation can append immutable content snapshots under the existing Goal ID. It does not assert that a Draft is executable or bypass its normal initial lifecycle.

## 4. Proposed command contracts

These are domain/API contract proposals for review, not deployed OpenAPI definitions. Physical storage and exact URL naming can be finalized after review; the required behavior is not optional.

### 4.1 Common command envelope

Mutation commands carry:

- A caller-generated command/idempotency key scoped to authenticated employee and command kind.
- Explicit target/source identifiers, not a client-selected owner or actor.
- Expected Goal content/operative and, when affected, relationship/proposal revisions.
- An exact reviewed payload/selection and nonblank business reason where required.
- Source/proposal provenance when derived from documents or Jira.

Server responsibilities:

1. Authenticate and authorize every referenced resource; infer actor from identity.
2. Resolve a completed receipt for an identical authorized retry before treating newer state as a fresh mutation.
3. Reject same key with a different behavior-affecting payload.
4. Revalidate exact expected revisions and the final graph under the command's serialization boundary.
5. Commit all effects, audit and result receipt together; no external calls inside that transaction.
6. Return command identity, changed/created Goal IDs, version/context identities, effective time and resulting eligibility.

Expected revisions are comparison tokens, not editable version numbers to substitute on retry. Bulk selections include their exact member sets and impact baselines. All-or-nothing behavior applies to the whole accepted command.

### 4.2 Command catalog

Routes below are proposed relative to `/api/v1`. Existing routes are identified separately in section 8.

| Command / suggested route | Required intent and checks | Result / forbidden effects |
|---|---|---|
| Create / `POST /goals` | Owned eligible parent/source; valid supported fields and dates | New Goal ID, Draft, initial snapshot; no implicit approval/activation |
| Prepare definition / `POST /goals/{id}/definition-proposals` | Expected current/proposal context; complete intended semantic changes | Reviewable immutable snapshot reference and diff; no operative mutation |
| Validate proposal / `POST /goals/{id}/definition-proposals/{proposal_id}/validate` | Exact snapshot; deterministic validation before provider work | Persist validation bound to evaluated inputs; no publication |
| Publish / `POST /goals/{id}/definition-publications` | Exact proposal and expected operative context, READY evidence, reason, employee attestation, resolved impact selection | Same Goal ID, new operative selection and history; lifecycle unchanged |
| Descope / `POST /goals/{id}/descope` | Reason, full affected-tree preview/baseline and ownership | Atomic permanent structural-subtree freeze; statuses/history preserved; no lineage traversal |
| Continue / `POST /goals/{id}/continuations` | Remaining scope, eligible next-quarter context, expected predecessor/tree and lineage, reason | New Draft plus predecessor freeze in one commit; no copying scores/approvals |
| Replace Completed / `POST /goals/{id}/replacements` | Source still Completed; new commitment, reason and valid destination context | New Draft, replacement link and recursive original freeze; old completion unchanged |
| Request reuse / `POST /goals/{id}/evidence-reuse-requests` | Exact target definition, selected owned source mapping/content, relevance | New pending target applicability/review; original approval untouched |
| Decide reuse / reuse of existing evidence-decision infrastructure | Authorized manager, exact submitted content/context, still-reviewable request | Independent decision for target context only; no Goal approval |
| Apply source plan / proposed plan-application command | Exact reviewed operation revision/subset, dependencies, attestation for included publications | One atomic receipt; new Goals Draft, only explicitly confirmed eligible changes published |

Descope, continuation, replacement and reuse contracts are bounded behavioral requirements. Their deferred subcases remain gated under section 11; this document does not approve their unresolved branches.

### 4.3 Publication request example

Illustrative names only:

```json
{
  "command_id": "employee-generated-unique-command",
  "proposal_id": "proposal-42",
  "expected_operative_version_id": "goal-version-7",
  "expected_proposal_revision": 3,
  "expected_relationship_revision": 2,
  "validation_run_id": "ready-run-for-exact-proposal",
  "change_reason": "Agreed revised operational automation commitment",
  "manager_discussed": true,
  "impact_preview_id": "reviewed-impact-preview-9"
}
```

The employee cannot set actor, manager approval, status, effective timestamp or arbitrary manager identity through this payload. Resolve the relevant manager context from trusted identity/profile information and record the attestation as an employee statement.

### 4.4 Publication sequence and validation binding

1. Prepare an immutable proposal without changing operative Goal/criteria/milestones.
2. Validate deterministic rules and obtain/persist semantic READY validation outside the mutation transaction.
3. Present complete diff, affected children, evidence implications and historical-reference exceptions.
4. Obtain explicit reason and employee confirmation.
5. Under locks, recheck proposal fingerprint, expected current context and the exact READY run.
6. Verify final dates/ownership/references and unchanged validation-relevant context.
7. Publish the exact validated proposal; update necessary current projections, parent context and audit atomically.
8. Leave lifecycle unchanged. Old evidence/results remain in their original context; new applicability requires the agreed evidence review.

Editing a proposal invalidates its previous READY/acceptance binding. A successful validation against one snapshot cannot authorize another. Store late validation results for the evaluated context, but report supersession rather than publishing newer inputs.

Use the existing latest-validation-result policy for an exact snapshot: an older READY must not silently override a newer non-READY result for that same input/context. Revalidate dynamic context at commit rather than trusting a preview or a token alone.

Publication time is server-authored UTC, effective on successful commit. A rolled-back command never becomes operative. Require deterministic event ordering for same-time operations; do not pretend transaction-start timestamps alone establish commit order.

### 4.5 Initial lifecycle versus revised ongoing publication

| State/context | Contract |
|---|---|
| New/unapproved Draft | Edit/prepare under same ID; existing normal validation/approval/activation requirements remain |
| Approved or Active ongoing commitment | Exact READY plus employee publication; no extra formal approval; current lifecycle unchanged |
| Active with uncommitted proposal | Continue using operative definition and its eligible evidence; proposal does not suspend execution |
| Completed, new material commitment | New Draft replacement; do not mark changed commitment Completed |
| Descoped/frozen source | Read history; reject definition/execution mutation |
| Archived source | Preserve existing lifecycle restrictions; no new publication path may become an implicit unarchive |

For initial creation, the approved definition and subsequent activation must refer to the same explicitly selected context. Do not equate Draft content with executable operative state. Exact initial selection storage is deferred to physical design.

READY validation is a quality gate, not evidence of manager approval. Phase 1 must update the current approval/eligibility logic so revised ongoing publication is usable without reintroducing a redundant approval operation. Preserve authorization and lifecycle gates, not the superseded "latest snapshot must have a new approval row" behavior.

### 4.6 Errors and retries

Reuse the existing v1 `error.code/message/details` envelope. Add typed domain codes through existing handling instead of creating a second error format.

| Condition | Proposed HTTP behavior |
|---|---|
| Missing/invalid authentication | 401 |
| Explicit authenticated actor/user mismatch or forbidden action | 403, consistent with existing identity policy |
| Target/reference not found or not visible to caller | 404 without cross-owner disclosure |
| Stale version/tree/selection, frozen target, conflicting lineage or key reuse | 409 with typed details and safe refresh guidance |
| Invalid fields, dates, attestation or unresolved required selection | 422 |
| Missing/non-READY/stale validation state | 409; no mutation |
| Provider unavailable during validation/retrieval | Explicit provider-class error through existing policy; no success-shaped fallback |
| Identical committed retry | Original authorized receipt; no new effects |

Proposed domain code examples: `STALE_CONTEXT`, `GOAL_READ_ONLY`, `VALIDATION_REQUIRED`, `IDEMPOTENCY_CONFLICT`, `IMPACT_REVIEW_REQUIRED`. These are not currently implemented codes.

## 5. Read contracts, execution eligibility and audit

### Read modes

| Mode | Required output semantics |
|---|---|
| Current | Exact operative definition, lifecycle and separate execution/disposition reason; unresolved proposal is labelled separately |
| Proposed | Exact proposal, source baseline, deterministic diff, READY status and reviewed impact selection; never presented as current achievement |
| Version history | Immutable snapshots plus explicit publication history; distinguish created time from became-operative time |
| As-of | Resolve definition, relationships, disposition and assessment inputs effective in the selected historical context |
| Structural hierarchy | Can show completed/frozen nodes with clear badges; visibility does not grant execution/contribution |
| Current measures/evidence | Filter by eligible current context and approved applicability before aggregation |

Suggested extensions: version/history and proposal resources under the Goal, plus explicit `view`/`as_of` context on contextual reads. Reject incompatible selectors instead of silently choosing one. Existing current detail URLs continue addressing the same Goal identity.

Every context-sensitive response should identify its resolved Goal/version/context, server-as-of time, execution eligibility and historical coverage limitations. Do not return an unexplained numeric zero for unassessed work.

Historical reads must not run LLM/providers, refresh evidence, mutate staleness state or commit caller-session changes. Incomplete legacy history is explicitly unknown or cutover-limited; never reconstruct approvals or execution dates from assumptions.

### Mutation/eligibility matrix

| Context | Definition prepare/publish | Progress/evidence/assessment execution | Structure/history |
|---|---|---|---|
| Ordinary mutable Draft | Preparation allowed; initial workflow retained | Existing eligibility requirements; not executable merely because Draft exists | Owned eligible structural changes; readable history |
| Eligible ongoing approved/current Goal | Explicit version-bound publication | Existing lifecycle plus current-version/applicability checks | Reviewed structural changes, dates and events |
| Completed commitment | No in-place new-commitment publication | No new execution masquerading as old completion | Read historical context; explicit replacement |
| Descoped subtree | Forbidden | Forbidden | Read only; no attach/detach/reparent/delete bypass; no reinstatement |
| Continuation predecessor | Definition/progress/new evidence/new assessment forbidden | Remaining work belongs to continuation | Lifecycle/relationship edge decisions remain gated until Phase 5 |

No client or job may infer eligibility from `status == Active` alone. Freeze must also be checked immediately before committing late work. Current execution aggregation excludes non-executable predecessors/frozen work; historical lifecycle can still say Active.

### Audit invariants

Record authenticated actor, command correlation, source/reason, old/new definition context, exact reviewed selection, UTC effective event ordering and result. Keep lifecycle, descoping, continuation and publication events distinguishable.

Evidence review additionally identifies exact content, reviewed metadata/association, target definition, manager decision and prior source context. Original records remain; a pending new review never upgrades their applicability.

Completed historical attribution is not current Annual achievement. Reassociation/replanning cannot move old completion dates or silently transfer assessment scores.

## 8. Compatibility and transaction contract

### Route migration

- Preserve existing `GET /goals/{id}` identity and default current read behavior; add contextual metadata deliberately.
- Existing `PUT /goals/{id}` may retain safe Draft-edit behavior. It must not continue directly publishing an ongoing protected definition without new preconditions.
- Revised clients use explicit preparation/publication. Old protected-edit callers receive an actionable typed conflict, not a silent successful no-op or a secretly published change.
- Existing evidence create/link/decision paths use the shared applicability infrastructure; no second evidence engine.
- Old approval/activation endpoints cannot bypass version eligibility or apply actions to frozen work.
- Deprecation and feature-capability gates must cover old workers/clients before enabling new write behavior.

### Mutation coordinator

Use one outer transaction per accepted command. Helpers stage and raise typed errors; they do not commit/rollback the shared transaction. Preserve the existing hierarchy lock contract when structure/context is involved. Document and enforce one deterministic resource-lock order across Goal, criterion, evidence, approval and job writers.

No LLM, document extraction, OAuth refresh or Jira call inside the mutation transaction. Validate outside, then check exact fingerprints/context inside.

Serialize hierarchy-dependent closure before reading/writing full subtree membership. Concurrent freeze, completion, child creation or reparenting cannot escape the command's final validated boundary.

Persist notifications or an outbox with the result, deliver externally after commit and deduplicate. A notification failure is not permission to repeat a completed business mutation.

Physical constraints, migrations and lock implementation details remain for the later reviewed design. SQLite baseline tests do not establish this contract.
