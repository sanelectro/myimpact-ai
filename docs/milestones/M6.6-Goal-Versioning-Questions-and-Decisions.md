# M6.6 - Goal Versioning: Questions and Decisions

**Status:** Product design draft, updated 2026-11-23. This describes the intended final product, not current app behavior or MVP scope. Where older M6.6 drafts differ, use the decisions below for the cases covered here. Recommendations and unresolved details are identified separately. See the [M6.6 workstream map](./M6.6-Implementation-Plan-Final-Draft.md#0-current-m66-workstream-map) for how this work fits into the wider milestone.

## 1. Goal identity, versions, and activation

**Scenario:** An employee has an active goal to reduce support response time by 20%. The target changes to 30%.

**Question:** Do we overwrite the active goal, create a new goal, or revise it?

**Decision:** Keep the same employee-owned goal ID and create v2 as a separate draft. Creating v2 immediately deactivates v1; v1 and its milestones remain visible in Goal History. There is no active version of this goal while v2 is in draft or approved but not yet activated. A materially different commitment gets a new goal ID rather than replacing the meaning of the old one.

1. The employee creates v2; v1 is deactivated and v2 starts as Draft.
2. The manager formally approves the exact v2 goal definition and every milestone included in v2. Approval and activation are separate: approval alone does not make v2 active.
3. The employee explicitly activates v2 when ready. The employee can obtain approval for multiple goals and activate them one by one.
4. Only after v2 is active can the employee select historical evidence for reuse and submit it for fresh manager review against v2.

If v2 is discarded or deactivated, both v1 and v2 remain inactive. The employee may create a fresh version or reactivate an older one. Reactivation preserves evidence approvals already granted for that same version; it does not transfer approvals from another version. At most one version of a given goal is active at a time.

**Reactivation:** Before reactivating v1, discard an open v2 draft or deactivate active v2. For a parent revision with automatically created descendant drafts, deactivate those descendant versions with the parent; the employee does not have to discard each child draft separately. v1 retains its existing manager goal approval, evidence approvals, milestone approvals, and milestone completion. Previously pending evidence reviews require new review requests; they are not automatically resumed.

**Expected behavior:**

- The planned model uses `goals` for identity, ownership, lifecycle and the active-version selection, and `goal_versions` for immutable definition snapshots. There can be no active version; readers must not fall back to v1 or treat a draft as active. The exact database representation of inactivity and reactivation needs design review.
- Creating v2 and deactivating v1 must be atomic. Activation must recheck the exact goal definition, validation, manager approvals, included milestones, and applicable schedule rules in one transaction. If activation fails, no version becomes active automatically; the prior deactivation remains in effect. An explicitly applied batch must succeed or fail together.
- Current screens, reports, and background jobs use the same active-version selection and clearly show the no-active-version state. Historical views preserve the original definition and associated records. A successful validation result or goal approval is not activation.
- Manager approval of the goal version is a formal decision. It is separate from milestone approvals, evidence reviews, and the employee's explicit activation action. The prior employee reason and manager-discussion attestation are distinct from manager approval.

### Example: a revised parent versus a new parent

The IDs below are illustrative labels, not a requirement that database IDs encode hierarchy. A goal ID identifies the goal; the version number identifies a definition of that goal.

**Revising an existing parent:**

```text
Before:
G1 v1       Annual: Improve customer checkout       [Active]
  G1.1 v1   Quarterly: Roll out checkout            [Completed]

After creating a revision:
G1 v2       Same annual goal, revised               [Draft]
  G1.1 v2   New draft of the same child goal        [Draft]
             Previous G1.1 v1 status: Completed
```

Creating G1 v2 deactivates G1 v1 and creates drafts for all descendants as described in section 4. G1.1 v1 remains Completed and available in history. G1.1 v2 starts as Draft because the prior completion may not apply to the revised parent. After the required goal and milestone approvals, the employee may activate it when its parent is active; it does not inherit v1's completion or progress.

**Creating a separate parent:**

```text
G1 v1       Annual: Improve customer checkout
  G1.1 v1   Quarterly: Roll out checkout            [Completed]

G2 v1       A separate annual goal
  G2.1 v1   Another quarterly goal
  G2.2 v1   Quarterly: Improve checkout speed       [New Draft]
```

G2 is a **new goal ID**, not a version of G1. New work can be created directly as G2.2 under G2; there is no need to create G1.2 first. An optional link from G2.2 to G1.1 can provide historical context; it does not change G1.1's completion or transfer its approvals, evidence, or progress. G2.2 follows its own approval and activation rules. Creating a separate G2 is not itself a revision or an instruction to deactivate G1.

## 2. Goal History, evidence reuse, and reviews on hold

**Scenario:** Evidence E17 was approved for v1's 20% target. Another v1 evidence review is pending when the employee starts drafting v2.

**Question:** What can the employee reuse, and what can the manager review?

**Decision:** Goal History shows deactivated versions with their evidence, decisions, milestones, and assessments. **Only after v2 is activated**, the employee may select evidence from history and request a new manager review against v2. Reuse links the same evidence record; it does not duplicate it, remove it from v1, or transfer an approval. It does not count for v2 until approved for v2. An old score remains historical; the new version starts not yet assessed.

| What happens to v2? | What happens to pending v1 evidence reviews? |
|---|---|
| v2 is created and v1 is deactivated | Hold pending v1 reviews. Explain the hold to employee and manager, and remind the employee to resolve the draft. No automatic expiry or unhold. |
| v2 is discarded or deactivated | v1 remains inactive; do not automatically resume its pending reviews. The employee may choose to reactivate an older version or create a fresh one. |
| v2 is activated | Close pending v1 reviews as superseded, not rejected. Evidence selected for reuse after activation gets a separate review against v2. |
| v1 is reactivated | Its previously approved evidence retains its approval for v1. Previously pending reviews require new requests, including those closed as superseded. |

**Expected behavior:** Prior decisions remain in history. A manager who opened a v1 review before deactivation cannot submit a decision during the hold or after v1 is superseded. The server rechecks the hold and version on submission, including concurrent revision and review actions. The hold applies to v1 evidence reviews, not to the v2 goal and milestone reviews required for activation.

## 3. Milestones in a new version

**Scenario:** v1 had three milestones, one already complete. The employee copies one unchanged, modifies another, and leaves the third behind.

**Question:** What carries over, and when can v2 go live?

**Decision:** The employee chooses which milestone definitions to copy, edit, or omit. **Every milestone included in v2 needs fresh manager approval**, even if copied unchanged. Copying transfers the definition, not the approval, completion, or progress. v2 cannot be activated while any included milestone is pending or rejected.

**Expected behavior:** The manager can review proposed v2 milestones while v1 is inactive and v2 is in draft. If an approved v2 milestone definition changes, it needs fresh approval for that changed definition. v1 and its milestones are deactivated when v2 is created; their prior approvals, completion, and progress remain read-only in Goal History.

### Manager grouped goal approval

The manager can select previously approved parent and child goal versions and unchanged milestones for a grouped fresh approval of their proposed versions, rather than approving each individually. **Only unchanged definitions are eligible** for grouped approval; changed goals or milestones must be reviewed individually. The employee and manager can inspect each previous version's status, description, and other details, and see the proposed definition before approval. The previous status is information, not an inherited decision.

The grouped action must create a fresh manager decision for each selected, authorized goal version and milestone and succeed or fail as one batch. The system must recheck the selected exact definitions, previous approval and unchanged status when the manager submits; a changed or stale selection must not be silently approved. Grouped approval does not activate the goals: the employee activates them separately and parent-first. Every included milestone still needs its own fresh approval, whether in a group or individually.

## 4. Roadmap, Adhoc, and Stretch hierarchy

**Scenario:** An unplanned sprint goal has no monthly Roadmap parent. Another sprint goal supports a real May Roadmap commitment, but its sprint runs May 25 to June 5.

**Question:** Do we create monthly placeholder parents, and does crossing month-end create a conflict?

**Discussed direction:** Roadmap goals follow Annual > Quarterly > Monthly > Sprint. Adhoc and Stretch are separate categories. Group unparented work in those categories together rather than generating placeholder goals such as `Adhoc-May-2026`. A month filter can provide a monthly view without creating a parent. If a goal has a real parent, the link is meaningful regardless of category.

**Expected behavior:** A sprint goal can cross month-end when its sprint does. Validate the sprint estimate against its assigned sprint window. The May label alone does not impose a May 31 hard deadline. For Roadmap work, keep the real parent and treat month-end and quarter-end as reporting checkpoints by default. A plan outside the assigned sprint or against an explicit hard deadline is a separate scheduling issue; do not hide it by changing the category or silently moving children.

**Recommendation:** A Roadmap draft may show **Parent needed** while being prepared, but should have the correct real parent before activation. A commitment deliberately planned across multiple sprints can be tracked at the appropriate higher level, with separate sprint deliverables where useful.

### Hierarchy deactivation and reactivation

**Scenario:** Creating annual v2 deactivates annual v1, which has quarterly, monthly, and sprint descendants.

**Decision:** Creating a parent revision also creates a new draft version of **every descendant**, including those that were completed or already inactive. Each draft keeps the same child goal ID and preserves the corresponding parent-child structure. Deactivate the old active descendant hierarchy, preserving the old goals, versions, evidence, milestone history, and assessments. Parent and descendant draft creation and hierarchy deactivation must succeed or fail together. Completed descendants remain historically completed; deactivation must not rewrite them as unfinished or erase their history. The new versions use the next available version numbers, which need not literally be v2.

**Source for each new descendant draft:** Use that child's latest goal version, including when it is inactive or was an unapproved draft. For example, if G1.1 v1 says "all customers" and the later G1.1 v2 says "two regions", the generated G1.1 v3 starts from v2. The employee can review and modify the draft before approval; its source version's approval, completion, and progress do not carry over. Record the source version so it can be displayed and audited. Recheck the latest versions as part of the atomic creation operation; do not silently use a stale source if a child changes concurrently.

These new descendant versions follow the goal and milestone approval and separate activation process; old approval, milestone completion, and progress do not automatically carry into a new version. Evidence reuse follows the after-activation rule. If the new parent version is discarded or deactivated, its descendant versions are also deactivated and preserved, not deleted.

Each descendant's new version starts as Draft, and the employee and manager can view the corresponding old version's status, description, and other details at any time. This includes a prior Completed status: it is shown as context, not silently copied as completion or progress. The employee can submit the new draft for manager review and activate it after the required goal and milestone approvals when its parent is active. The old completed version stays completed.

**Parent-first activation:** A child goal cannot be activated or reactivated until its immediate parent is active. This applies at every level: Annual before Quarterly, Quarterly before Monthly, and Monthly before Sprint. Creating or preparing a child draft does not itself activate it.

If annual v2 is discarded or deactivated and annual v1 is reactivated, automatically reactivate the descendants that were active before the hierarchy deactivation, preserving their own existing approvals and milestone completion. A completed child keeps its **Completed** status and its history; do not reopen it or reactivate it as ongoing work. Keep the newly created descendant versions deactivated in history; do not require individual child-draft discards. Reactivate parent first, then descendants in hierarchy order, as one operation; if the operation cannot complete safely, do not partially reactivate the hierarchy. Do not automatically activate descendants that were already inactive or completed. The implementation must preserve the information needed to distinguish these cases and enforce at most one active version per goal.

**Open details:** The implementation must distinguish product-visible goal versions from technical observation records when selecting the latest source; how to map legacy records safely requires design review. The newly agreed ability to activate a draft of a completed descendant applies to a parent revision; the boundary between that case and a materially different commitment requiring a new goal ID still needs clarification. Define how automatic hierarchy reactivation handles descendants that were independently changed or now have a conflicting active version. Do not silently overwrite those changes; resolve these policies before implementing the affected cases.

## 5. Estimated dates, actual dates, and continuations

**Scenario:** Work estimated for May finishes in June, or the employee chooses to track the remaining work separately in a later sprint.

**Question:** Which dates change, and when is a `-part2` goal needed?

**Decision:** Let the employee decide the new version's `EstimatedStartDate`, `EstimatedEndDate`, `ActualStartDate`, and `ActualEndDate`. Show the corresponding previous-version date below each field as reference. Keep the previous version's dates and completion history unchanged; a displayed previous date is not itself a value for the new version or proof that it is completed.

The date model must distinguish the dates of each version, including when a completed child's new version starts fresh under the same goal ID. The precise storage design and whether the new fields are prefilled are not yet decided. **Entering an actual end date does not complete the version.** The employee must explicitly use **Mark complete** for v2, even if v1 was completed or an actual end date has been entered. Keep system-recorded completion transitions and their version context for reporting; do not overwrite a historical completion. Reporting uses when completion was recorded, not a manually entered earlier actual end date.

| Situation | Expected behavior |
|---|---|
| Work simply runs late | Record the actual dates. Keep the original estimate and parent. Do not create a revision or a `-part2` automatically. |
| The same commitment is formally rescheduled | Revise its estimated dates without losing the original estimate. Keep the original Roadmap reporting period; show spillover rather than reparenting just because the work runs into a new period. |
| Remaining work becomes a separately tracked commitment | The employee explicitly creates a linked `-part2` draft with a new goal ID, its own dates, and the appropriate parent for the new work. Part 1 keeps its history. |

**Important distinction:** A revision changes the definition of the same commitment. A continuation is a separate commitment, like cloning a Jira ticket for a later sprint. Creating it does not fix a date conflict in Part 1 or transfer Part 1's approval or progress.

## 6. Month-end, quarter-end, and year-end carryover

**Scenario:** A May Roadmap goal stays open beyond May 31. It might finish in June, July, or even in the next year.

**Question:** Where is the goal shown, and which reporting checkpoints does it meet?

**Confirmed decisions:** Use **calendar quarters**. Month-end, quarter-end, and year-end report what was complete at the cutoff; quarter-end is not a hard deadline by default. Keep the original Roadmap parent. Show open work in the next period's **Carryover** view using the same goal, evidence, and progress, without creating a duplicate or counting the same work twice.

| Example | Expected result |
|---|---|
| A May goal is marked complete June 12 | Not complete at May month-end; complete by Q2 end on June 30. |
| A May goal is marked complete July 10 | Not complete at May month-end or Q2 end. It later shows completed and can contribute once to its original annual outcome. |
| Work finished June 29 but the employee only marks it complete July 2 | Not complete at Q2 end. The timestamp when MyImpact records completion matters, not a manually entered earlier `ActualEndDate`. |
| A December 2026 goal is marked complete January 12, 2027 | Not complete at 2026 year-end. Show it as 2026 carryover in 2027 and then as completed January 12. It stays linked to the 2026 Roadmap; no 2027 annual credit. |

**Expected behavior:** Employees mark their goals complete promptly. No recorded completion means the goal is not marked done. Late completion does not automatically reduce annual achievement unless timing was part of the success criteria. A completed child contributes to an annual outcome; it does not automatically prove that outcome was achieved.

## 7. Correcting a mistaken completion

**Scenario:** An employee marked a checkout rollout complete June 29, then discovered July 2 that it reached only half the customers.

**Question:** How can the employee correct it without silently rewriting the Q2 report?

**Confirmed decision:** Use an explicit **Correct completion** action with a reason. Return the goal to **In progress** and retain the original completion and the correction in history. Preserve the originally reported Q2 result and annotate it, for example: **Reported complete at Q2 end; corrected July 2**.

**Expected behavior:** When the employee marks the goal complete again, record the new completion time and count the goal only once toward the annual outcome. If the original goal really was completed and new work comes up later, leave it closed and create a linked follow-up goal instead.

## 8. Implementation boundaries and remaining details

- **Current state:** The revision panel can prepare, preview, and validate a proposal while keeping the current goal unchanged; the newly agreed immediate-deactivation flow is not implemented. Publication is not available, and the legacy **Edit goal** path still edits the live goal directly. Do not enable the new activation flow while current readers and writers can disagree about the active definition or while approvals and assessments can be misattributed.
- **Legacy data:** Preserve planned dates where their meaning is known. Do not invent actual dates, historic completion times, or version associations for older approvals where the source data cannot prove them.
- **Details not finalized here:** The reporting cutoff time zone, reminder cadence and delivery, the exact way users declare and resolve an explicit hard deadline, and conflicts caused by independently changed descendants during hierarchy reactivation. Older strict parent-date checks need to distinguish Roadmap reporting checkpoints from genuine scheduling constraints.
- **Release checks:** Exercise atomic parent and all-descendant draft creation and recursive hierarchy deactivation with rollback, including completed and inactive descendants; group deactivation of new descendants; no-active-version reads; failed activation without automatic v1 reactivation; formal goal and exact milestone approvals; activation one goal at a time; discarded or deactivated v2; older-version reactivation and retained same-version approvals and milestone state; parent-first atomic restoration of only previously active descendants without individual child-draft discards; stale manager review submissions and new requests after reactivation; evidence reuse only after activation with fresh approval; carryover without duplicate credit; and a completion correction after a cutoff.

### 9.3 Negative scenarios and safeguards

| ID | Attempt or failure | Expected result |
|---|---|---|
| N1 | Activate v2 while the goal manager approval is missing or while any included milestone is pending or rejected. | Block activation and show the missing approval. Do not make v1 active again automatically. |
| N2 | Activate or reactivate a child while its immediate parent is inactive. | Block the child action and identify the inactive parent. Restore or activate the parent first. |
| N3 | Reactivate v1 while an active v2 has not been deactivated, or while an ordinary open v2 draft has not been discarded. | Block the conflicting action; do not make two versions active. The group restoration exception for automatically created descendant drafts is described in H6. |
| N4 | Copy historical evidence to v2 before v2 is active, or count it while its v2 review is pending or rejected. | Block reuse before activation. Once requested, do not count the evidence for v2 without a fresh approval for v2. |
| N5 | A manager submits a held v1 evidence review or a review closed as superseded. | Reject the submission; do not approve or reject it for either version. Reactivating v1 requires a new request for previously pending evidence. |
| N6 | Parent revision creation fails after some child drafts were prepared or some old descendants were deactivated. | Roll back the entire operation: no partial descendant drafts or deactivations persist, and the pre-operation state remains unchanged. |
| N7 | Automatic restoration cannot safely restore every required previously active descendant. | Do not partially restore the hierarchy or silently overwrite independent changes. Explain the conflict. The precise resolution policy for independently changed or conflicting descendants is **Open**. |
| N8 | The live selection is empty while v2 is Draft or approved but inactive. | Do not show v1 or v2 as active by falling back to the latest version. Show the no-active-version state consistently. |
| N9 | A v2 proposal is validated, but its exact definition or required approval has since changed. | Do not treat an obsolete validation or milestone approval as sufficient for activation. Recheck the exact candidate and its required current approvals. |
| N10 | An employee without ownership, or a person without the required manager authority, tries to perform the corresponding action. | Reject the unauthorized action on the server; do not change versions, reviews, or history. |
| N11 | A revision causes a plan to exceed its assigned sprint window or conflict with an explicit hard deadline. | Surface the scheduling issue; do not hide it by changing category or silently moving children. Changed items require individual review. At submission, the selected batch must succeed or fail together. |

### 9.4 Decisions still needed

- **Completed descendants:** A parent revision creates an activatable draft for every child, including completed children; the old status is context, not inherited completion. Clarify the boundary between a revised child and genuinely different work requiring a new ID. The old completed version remains completed.
- **Date entry:** Decide whether new version date fields start blank or are prefilled. Previous-version dates shown as reference or entered into v2 must not silently complete the new version; completion requires the separate Mark complete action.
- **Legacy and technical version records:** Define how the latest product-visible child version is identified when technical observations or ambiguous legacy snapshots are present, without inventing historical approval or state.
- **Hierarchy restoration conflicts:** Decide how to resolve independent child changes or conflicting versions without silently losing work or partially restoring the hierarchy.
- **Approval invalidation:** Confirm the exact review behavior if the goal definition itself changes after manager approval, including whether and how existing milestone approvals remain valid.
- **Reporting and scheduling details:** Choose the cutoff time zone, reminder cadence and delivery, and the hard-deadline declaration and resolution workflow. Decide how inactive versions are represented at a reporting checkpoint without inventing a completion or double-counting.
- **Evidence content changes:** Define how a review remains tied to the evidence content the manager actually reviewed if the underlying evidence can be edited. Same-version reactivation must not silently claim an approval covers changed content.
