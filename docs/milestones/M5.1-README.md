# M5.1 — API v1 Boundary & Contracts

## Goal

Establish the product-facing `/api/v1` boundary without changing the existing M3/M4 domain services or database schema.

## Boundary

Product APIs will live under:

```text
/api/v1/...
```

Existing internal/domain CRUD routes remain unchanged for now. M5 does not require migrating or deleting those routes yet.

## Contract principles

1. Product APIs describe user intent, not persistence internals.
2. Product APIs must not expose repositories, vector-search details, embedding models, chunk internals, or LLM implementation details.
3. User identity will be resolved at the product/API boundary when authentication is introduced; product routes should not require callers to supply an arbitrary `user_id` for the current-user context.
4. Product responses are resource/use-case responses rather than database-model dumps.
5. API contracts should remain stable even if internal services or persistence models change.
6. Pagination, filtering, and sorting will be added only where a product API requires them.

## Error contract

All `/api/v1` errors use:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": []
  }
}
```

`details` is optional. Validation errors include FastAPI validation details. HTTP errors use a stable HTTP-derived code such as `HTTP_404` until product-specific error codes are required.

Unhandled v1 errors return:

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "An unexpected error occurred"
  }
}
```

Legacy routes outside `/api/v1` retain their existing error behavior.

## Current implementation

- `/api/v1` router boundary created.
- Common v1 HTTP, validation, and unexpected-error handling established.
- No database changes.
- No M3/M4 service changes.
- No authentication implementation.
- No product use-case endpoint implemented yet.
