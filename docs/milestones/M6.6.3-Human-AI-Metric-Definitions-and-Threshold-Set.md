## 1. Objective

Define a transparent, versioned metric catalogue and proposed threshold
set for evaluating MyImpact AI assessments against human-reviewed
reference decisions.

The evaluation must measure three distinct dimensions:

1.  **Assessment correctness** --- whether AI decisions agree with
    human-approved ground truth.
2.  **Assessment consistency** --- whether repeated AI evaluations
    produce stable decisions and outputs.
3.  **Assessment robustness** --- whether AI behaves appropriately when
    evidence is missing, insufficient, irrelevant, contradictory, stale,
    inaccessible, or difficult to attribute.

Operational execution reliability must also be measured, but must not be
confused with assessment correctness.

This document proposes initial threshold values for review. **No
threshold in this document is approved.** Numeric values must be
reviewed against the finalized benchmark, category sample sizes, product
risk, and actual metric behavior before an authorized human approves the
threshold set.

## 3. Threshold governance principles

-   Thresholds are versioned data, not scattered hardcoded constants.
-   A threshold set is bound to compatible dataset, metric-definition,
    evaluation-code, and relevant configuration versions.
-   Human approval is explicit, authenticated, auditable, and immutable.
-   Copilot or an automated evaluation run must never approve a
    threshold set.
-   Draft or rejected thresholds cannot authorize a release decision.
-   Missing data, zero denominators, insufficient samples, or
    incompatible versions must not be silently treated as passing.
-   Exploratory results must remain distinct from governed
    release-evaluation results.
-   Critical safeguards must be treated as gates, not averaged away by
    strong performance elsewhere.
-   The original 14-case exploratory benchmark and its results must
    remain preserved.
-   The proposed expanded benchmark of up to 34 cases must not be
    considered approved ground truth until its case definitions and
    human reviews are complete.

## 4. Evaluation eligibility prerequisites

A release-oriented threshold comparison is eligible only when all
required prerequisites are satisfied:

1.  Dataset version is identified and frozen for the run.
2.  Required cases have complete assessment context.
3.  Category-specific human labels and AI-output mappings are
    documented.
4.  Two independent human reviews are complete for each required case.
5.  All disagreements requiring adjudication are resolved.
6.  Canonical reference labels are finalized and the dataset is marked
    with the existing approved state.
7.  Metric definitions are versioned.
8.  Threshold set is approved and compatible with the dataset and metric
    definitions.
9.  AI run records the model/provider identifier, prompt version,
    relevant generation settings, retrieval configuration, evaluation
    code version, schema version, and other available reproducibility
    metadata.
10. Required source retrieval and evidence provenance information is
    available for metrics that depend on it.

If a prerequisite is missing, return the project's equivalent of
`NOT_EVALUABLE`, `BLOCKED`, or `EXPLORATORY`. Do not return a release
`PASS`.

## 5. Proposed threshold catalogue

All values below are **proposals for review**, not approved product
policy. Apply a minimum sample-size rule before interpreting
percentages. If a metric cannot be calculated reliably for a category,
mark it `NOT_EVALUABLE` rather than passing it.

## 6. Minimum sample size and statistical limitations

The proposed expanded benchmark contains up to 34 cases. This is useful
for an initial governed benchmark, but it is small for strong
statistical claims, especially at category level.

Rules: - Report numerator, denominator, and case count for every
percentage. - Report per-category counts and class distribution. - Do
not approve a category-level threshold based on too few cases. - If a
category has no examples or too few eligible examples, mark its metric
`NOT_EVALUABLE`. - Do not interpret 4/4 correct as evidence that the
true category accuracy is 100%. - Use confidence intervals where
appropriate and explain their limitations for small samples. - Define a
minimum sample-size policy per metric before approval. The numeric
minimum must be decided by the benchmark owner based on intended use and
risk; do not invent it during implementation. - Expand high-risk
categories---attribution, citation grounding, quantitative claims,
evidence sufficiency, and contradiction handling---before making strong
release claims. - Do not silently pool unlike categories just to
increase sample size.

A threshold comparison is valid only if the benchmark has enough
eligible cases to support the metric. Otherwise, the result is
`NOT_EVALUABLE`, even if the observed percentage is high.

## 7. Overall evaluation decision logic

Do not use a simple weighted average of all metrics as the release
decision. Strong performance on easy categories must not conceal a
critical failure.

Use the existing project status model if one exists. Otherwise, propose
equivalent states:

  ---------------------------------------------------------------------
  Outcome                            Meaning
  ---------------------------------- ----------------------------------
  `PASS`                             All required prerequisites are
                                     met, all mandatory metrics are
                                     evaluable and meet approved
                                     thresholds, and no critical
                                     safeguard fails.

  `FAIL`                             Evaluation is eligible and
                                     complete, but one or more
                                     mandatory thresholds fail or a
                                     critical safeguard is violated.

  `NOT_EVALUABLE`                    Required sample size, reference
                                     labels, metric inputs, or
                                     compatible configuration is
                                     missing.

  `BLOCKED`                          Evaluation could not be completed
                                     because a required dependency,
                                     environment, permission, or
                                     service was unavailable.

  `EXPLORATORY`                      Results are available but
                                     dataset/threshold approval
                                     prerequisites are not satisfied.
  ---------------------------------------------------------------------

Rules: - `NOT_EVALUABLE`, `BLOCKED`, and `EXPLORATORY` are never
`PASS`. - A critical metric failure cannot be averaged away. - An
overall `PASS` requires every mandatory metric to be evaluable. -
Informational metrics may be reported without blocking only if that
treatment is explicitly approved in the threshold set. - Record which
exact threshold-set version was applied to the run.

## 8. Development and release profiles

Maintain two distinct profiles if the existing architecture supports
this separation.

### Profile A --- Development / exploratory

Purpose: - Prompt and model iteration. - Trend analysis and regression
discovery. - Investigation of weak categories. - Repeatability
experiments.

Rules: - May run against draft datasets. - May use provisional reference
labels, clearly marked as provisional. - Must not claim release
approval. - Threshold comparisons, if shown, must be labeled
exploratory. - Preserve run configuration and results.

### Profile B --- Release evaluation

Purpose: - Formal evaluation against human-approved reference
decisions. - Release gate for a specified model/prompt/configuration.

Prerequisites: - Human-reviewed and adjudicated dataset. - Approved
metric definitions. - Approved threshold set. - Compatible versions and
complete run metadata. - Required sample-size rules satisfied. -
Integrated validation completed where required.

A development profile must never silently become a release profile.

## 10. Per-metric definition requirements

Every metric must define:

1.  Stable metric ID and name.
2.  Purpose and category.
3.  Exact formula.
4.  Numerator and denominator.
5.  Unit and value range.
6.  Direction (`HIGHER_IS_BETTER` or `LOWER_IS_BETTER`).
7.  Threshold and comparison operator.
8.  Required inputs and eligible case population.
9.  Inclusion and exclusion rules.
10. Zero-denominator behavior.
11. Minimum sample-size requirement.
12. Handling of missing, invalid, or partial data.
13. Aggregation method.
14. Limitations and interpretation guidance.
15. Metric-definition version.

Do not implement a metric from its name alone. Confirm its formula and
data availability in the current codebase.

## 11. Metric comparison behavior

For each metric, the comparison must return one of: - `PASS` - `FAIL` -
`NOT_EVALUABLE`

or existing equivalent values.

Required behavior: - Missing numerator or denominator must not default
to zero in a way that creates a pass. - Zero denominator must follow the
metric's explicitly defined behavior. - Insufficient sample size must
return `NOT_EVALUABLE`. - Incompatible dataset/metric/threshold versions
must prevent a release pass. - A missing critical metric must prevent
overall `PASS`. - Report observed value, threshold, comparison operator,
numerator, denominator, sample size, and result. - Retain the exact
calculation/version metadata for auditability.

## Role-Aware AI--Human Evaluation Metrics (M6.6 addition)

### Purpose and boundary

These metrics evaluate whether the AI system interprets goals,
achievements, and evidence appropriately in the supplied role context.
They do **not** assess the employee's performance or decide whether the
employee meets, exceeds, or falls short of role expectations.

Role context is an input to selected evaluation dimensions; it is not a
substitute for evidence and is not itself ground truth.

### Metric classification

Keep metrics explicitly separated into the following groups.

#### A. Role-independent metrics

These must be assessed consistently across roles:

-   Factual correctness and claim support.
-   Citation reference validity.
-   Citation grounding correctness.
-   Contradiction detection.
-   Unsupported or fabricated claim rate.
-   Correct abstention when evidence is missing, inaccessible, or
    insufficient.
-   Structured-output validity and traceability.

Role title or seniority must not change whether a citation supports a
claim or whether a factual statement is fabricated.

#### B. Role-aware metrics

Evaluate these against the role context and, where required, the
authoritative role expectation/framework version supplied for the
assessment:

-   **Role-context use accuracy:** Whether the AI uses the supplied role
    context correctly and does not invent missing expectations.
-   **Role-relevant evidence precision:** Whether evidence selected as
    relevant is relevant to the stated role-related criterion or claim.
-   **Role-aware evidence sufficiency accuracy:** Whether the AI
    correctly identifies whether the supplied evidence is sufficient for
    the role-related conclusion.
-   **Contribution-scope accuracy:** Whether individual, team,
    cross-team, and organizational contribution are distinguished
    correctly.
-   **Attribution accuracy in role context:** Whether outcomes are
    attributed only to the individual to the extent supported by
    evidence.
-   **Role-aware impact interpretation accuracy:** Whether the
    interpreted scope and impact are supported by evidence and
    applicable role expectations.
-   **Historical role-context accuracy:** Whether the AI uses the
    role/framework version applicable to the assessment period when that
    information is supplied.

Do not calculate these metrics when the required role context or
human-reviewed reference is missing. Mark them `NOT_EVALUABLE` (or use
the existing equivalent).

### Paired and controlled evaluation design

The evaluation dataset should include controlled comparisons:

1.  **Same evidence, different roles:** Compare paired cases with
    identical evidence and different role contexts. Score whether
    contextual interpretation changes only where the supplied
    expectations justify it. Objective factual and citation checks
    should remain stable.
2.  **Same role, different evidence:** Hold role context constant and
    vary evidence quality. Verify that output changes track evidence
    quality.
3.  **Missing role context:** Verify that the AI does not infer role
    expectations from an absent or incomplete role description.
4.  **Historical role context:** Verify use of the applicable historical
    role/framework version rather than silently applying the current
    framework.
5.  **Team outcome and individual attribution:** Verify that the AI does
    not over-attribute team outcomes based on role or seniority.
6.  **Role expectation versus evidence conflict:** Verify that role
    expectations do not cause the AI to claim that an action occurred
    when the evidence does not support it.

A difference between paired outputs is not automatically a success or
failure. Scoring requires a human-reviewed expected rationale.

### Threshold treatment

The previously proposed numeric thresholds in this document remain draft
proposals and are **not approved**. The following governance rules apply
to role-aware metrics:

-   Do not invent or automatically approve numeric thresholds for newly
    introduced role-aware metrics.
-   Add role-aware metrics to the metric catalogue with definition,
    unit, numerator, denominator, eligibility rules, exclusions,
    aggregation method, minimum sample policy, and known limitations.
-   Have benchmark cases and expected rationales
    human-reviewed/adjudicated before using them as reference labels.
-   Approve thresholds through the existing authorized
    threshold-approval workflow.
-   Report role-aware metrics separately from role-independent metrics.
-   Do not hide a role-aware failure inside an overall weighted average.
-   Where a role or role-framework subgroup has insufficient eligible
    cases, report `NOT_EVALUABLE`; show the sample count and
    denominator.
-   Avoid comparing roles or levels as a ranking exercise unless a
    separately approved evaluation design explicitly supports that
    comparison.

### Reporting requirements

Every evaluation report should identify:

-   Role-independent metrics and results.
-   Role-aware metrics and results.
-   Role-context completeness and framework version coverage.
-   Number of eligible cases per metric and per role-context subgroup.
-   Human-review/adjudication status of reference labels.
-   Metrics marked `NOT_EVALUABLE` and why.
-   Whether the run is exploratory, development, or release evaluation.

The report must state clearly that role-aware evaluation measures the
AI's interpretation quality, not the employee's performance.

### Acceptance criteria

-   Role-independent and role-aware metrics are separately defined and
    reported.
-   Paired same-evidence/different-role cases are included in the
    evaluation design.
-   Missing and historical role context are tested.
-   No role-aware metric is scored against unreviewed expected labels as
    if they were ground truth.
-   New role-aware thresholds remain draft until formally approved.
-   Insufficient samples are marked `NOT_EVALUABLE`.
-   Role seniority alone cannot increase correctness, attribution, or
    impact scores.
