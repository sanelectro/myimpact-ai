# MyImpact — M6.8 Admin Portal and Platform Access

## Milestone overview

**Milestone:** M6.8  
**Status:** Implementation, API, UI, and database changes are present; integrated milestone validation is not yet recorded.

M6.8 tracks the expanded platform-access scope: user authentication, organization and reporting-manager relationships, and the platform-admin portal. M6.10 remains the final end-to-end release gate and must include these flows.

## Scope

- Authenticate users through the dedicated issuer, including registration, password sign-in, access tokens, refresh-token rotation, and logout.
- Protect product APIs by validating token signature, issuer, audience, expiry, scope, and user identity.
- Associate registration with a new or existing organization using normalized organization names.
- Let users manage company, engineering role, and reporting manager in their profile; enforce reporting-manager eligibility and organization membership at the API.
- Keep organization-scoped goals associated with the user's company while preserving user-level privacy.
- Provide a platform-admin portal for reviewing customer users' goals, impact, and evidence across companies; inviting users; and disabling or reactivating accounts.
- Keep platform-admin privileges separate from customer organizations and prevent public self-promotion.

## Acceptance checks

- [ ] Apply all current migrations to a fresh disposable database and verify the organization, reporting, authentication, and platform-admin schema.
- [ ] Test registration with both a new organization and a normalized match to an existing organization.
- [ ] Test sign-in, token issuance, refresh rotation, logout, invitation acceptance, expiry, and resend invalidation.
- [ ] Verify protected APIs reject missing, invalid, expired, wrong-issuer, wrong-audience, and insufficient-scope tokens.
- [ ] Verify existing users cannot be claimed by unauthenticated registration and document the approved password-provisioning path.
- [ ] Verify profile changes enforce organization membership and the reporting-manager role hierarchy at the API.
- [ ] Verify organization-scoped goals use the correct organization and remain private to their owning user.
- [ ] Verify only platform administrators can access admin routes and APIs; public registration cannot grant that role.
- [ ] Verify authorized cross-company review and ensure ordinary users cannot access other users' or organizations' data.
- [ ] Verify disabling an account blocks new sign-ins and revokes refresh sessions; verify reactivation behavior.
- [ ] Review production requirements for key management, HTTPS, secure cookies, trusted origins, email verification, and abuse protection.
- [ ] Add/run integrated API, UI, and browser tests for the user and admin journeys.

## Known deployment requirements and limitations

- Production signing keys must be managed outside source control; production must use HTTPS, secure cookies, canonical issuer URLs, and explicit allowed origins.
- Public registration needs email verification and abuse protection before production exposure.
- Existing pre-authentication users need an administrator-provisioned password before they can sign in.
- Platform-admin access is an operator role, not an organization administrator role. Cross-company access must remain explicit and tested.
