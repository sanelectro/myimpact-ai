# M6.6 Technical Plan — Goal Criteria and Evidence-Based Assessment

**Status:** Implementation in progress; product decisions are recorded in
[M6.6-README.md](./M6.6-README.md).  
**Scope:** Implement versioned goal criteria, source-grounded AI assessment,
deterministic progress, and consistent presentation on Goal detail and Goals.
**LLM design reference:** [M6.6 LLM Role and Prompts](./MyImpact-M6.6-LLM-Role-and-Prompts.md).

### Implementation snapshot

The implementation includes typed contracts, ORM models and migrations,
criteria generation/version/approval APIs, assessment persistence and
deterministic progress, feedback events, and Goal Detail/Goals presentation.
Reanalysis now refreshes authorized GitHub/Jira evidence through the existing
discovery flow before assessing current approved criteria. The synchronous
refresh is limited to the goal date range (at most 366 days), 10 GitHub commits,
5 pull-request lookups, 10 Jira issues, and 20 candidates per source. Retrieved
records are upserted by owner/source identity, changed content creates an
evidence version, new goal mappings remain pending review, and previous
assessment evidence preserves its title and source timestamps. Connector
failures are isolated; successful evidence can still be assessed and the run
reports `PARTIAL` with an explicit error. With no connected sources, existing
goal evidence is still assessed from its stored snapshot and the missing
connection is shown as a limitation when that goal has evidence from that
provider. A per-goal, per-provider refresh checkpoint limits subsequent source
queries to the checkpoint date with a one-day overlap; candidates at or before
the exact checkpoint are filtered before LLM summarization. Each checkpoint
advances only after that provider's discovery and evidence persistence succeed,
so failed providers retry from their prior checkpoint while successful
providers advance independently. This remains bounded retrieval, not complete
source-change detection: provider result caps and connector query semantics can
limit which changed records are returned.

The Goals page also has a synchronous bounded Analyze Goals action with
per-goal run results. Reanalysis now builds bounded provider search clauses
from each approved criterion, then asks the source-summary prompt to identify
criterion-relevant records and assess retrieval sufficiency before passing
newly discovered evidence to criterion assessment. Search terms are derived
from approved criterion definitions rather than generated by a separate
search-planning prompt. Interpretation, evidence matching, and final
criterion assessment remain combined in the criterion-assessment prompt.
A live test against the seeded demo goal `goal-user1-quality` used the configured
Groq provider and local PostgreSQL. It persisted four criteria as `PROPOSED`,
without promoting them to current. The first provider response failed JSON
validation; one retry succeeded. This validates the generation path, not AI
quality. The original local goal data was removed during the user-approved
database reset; the test used demo seed data instead.

The original 24 migrations were validated and applied from scratch to a
disposable PostgreSQL database and the reset local development database. The
M6.6 migration was aligned with the ORM index name; a schema comparison found
no M6.6 ORM differences. The additive evidence-metadata snapshot migration
validated and applied locally, advancing Flyway to `20261025110000`. The
per-goal source-fetch-state migration was then validated and applied locally;
Flyway now reports schema version `20261025135000`. Focused
assessment/retrieval validation passes 47 backend unit and integration tests;
the evidence-approval API test also passes. All 11 M6.6 Playwright tests and
the M6.3 and M6.5 Playwright tests pass.
Coverage includes criterion-targeted queries, retrieval sufficiency and
evidence scoping, feedback and review decisions, insufficient and contradictory
evidence, obsolete assessment history, loading/empty states, and failed-run
recovery. Service tests exercise database persistence with mocked external
connectors and model responses.

Focused validation now covers source refresh, evidence versioning, pending
review state, immutable assessment snapshots, partial connector failures, the
criterion-to-evidence workflow, assessment feedback persistence, criterion
revision invalidation, and the reanalysis UI. Background scheduled or
event-driven freshness checks are not required for M6.6; source refresh remains
user-triggered through reanalysis. M6.6 is **not release-ready or complete**:
last-verified presentation, broader source-access/API edge coverage, the full
human-reviewed evaluation dataset, and numeric quality thresholds remain open.
Fingerprint comparison marks changed inputs stale when summaries are read.

## 1. Current implementation and constraints

- Goals are stored in `goals`; they have a lifecycle independent of evidence
  and assessment ([goal model](../../app/db/models/goal.py)).
- Evidence is stored once and associated with goals through
  `evidence_mappings`; a mapping may also point to a goal milestone
  ([evidence mapping model](../../app/db/models/evidence_mapping.py)).
- Evidence records already carry source URLs, source modification time, and a
  content hash; extracted versions are stored in `evidence_versions`
  ([evidence model](../../app/db/models/evidence.py),
  [version model](../../app/db/models/evidence_version.py)).
- Manager review is already tracked per evidence mapping in
  `evidence_approvals`, including pending, approved, rejected, and
  needs-information states. M6.6 should read and display that state, not create
  a second manager-review workflow
  ([approval model](../../app/db/models/evidence_approval.py)).
- `GET /goals/{goal_id}/assessment` currently calculates progress from a fixed
  target of three impact-bearing evidence items
  ([route](../../app/api/v1/goal_assessment.py),
  [service](../../app/services/goal_assessment.py)). Goal detail and Goals
  consume this legacy response
  ([GoalDetailPage](../../../myimpact-web/src/pages/Goals/GoalDetailPage.tsx),
  [GoalsPage](../../../myimpact-web/src/pages/Goals/GoalsPage.tsx)).
- Document expectations are extracted from uploaded expectation documents;
  they are not user-approved goal criteria and should not be reused as the
  criteria persistence model
  ([expectation model](../../app/models/expectation.py),
  [extraction service](../../app/services/document_expectation.py)).
- Existing evidence-evaluation code provides prior art for structured LLM
  output validation and explicit provider/validation errors
  ([evidence evaluation](../../app/services/knowledge/evidence_evaluation.py)).
- GitHub and Jira retrieval already use authorized source connections and
  direct APIs ([evidence discovery](../../app/services/evidence_discovery.py),
  [source connections](../../app/services/source_connections.py)). The
  `app/mcp` package currently has no implemented adapters. Treat MCP as an
  optional retrieval adapter to investigate, not as an existing capability;
  do not assume Confluence or additional tools are available.

## 2. Target architecture

Keep the existing service-oriented application structure. Do not introduce a
new service or a separate evidence store.

1. **Criteria service:** Creates AI-proposed or manually authored criteria,
   validates edits, versions definitions, and records employee approval.
2. **Assessment service:** Selects authorized evidence mapped to the goal,
   plans targeted searches, retrieves supported source content, asks the model
   for structured interpretation/matching/criterion assessments, validates all
   returned IDs and citations, and persists immutable assessment results.
3. **Progress aggregator:** Pure deterministic backend logic computes
   criterion progress, goal progress, criteria-met counts, and evidence
   coverage. The LLM does not calculate or override these aggregates.
4. **Freshness/invalidation service:** Compares goal, criterion, evidence, and
   assessment-rule fingerprints; marks affected results stale and schedules or
   requests targeted reassessment.
5. **API/UI:** Goal detail manages criteria and assessments; the Goals page
   displays summaries returned by the same aggregation logic.

Keep `goals.status` and `goals.sub_status` separate from criterion result and
assessment lifecycle. Completing a goal must not set a criterion to `MET`.

## 3. Data model and migration

Add a versioned database migration using the existing migration conventions.
Prefer stable criterion identity plus immutable versions and assessment
records; do not store only a mutable JSON result on `goals`.

### Proposed tables

| Table | Purpose |
|---|---|
| `goal_criteria` | Stable criterion ID, goal ID, current version pointer, active/retired state, creator, timestamps. A goal owns its criteria. |
| `goal_criterion_versions` | Immutable version number, criterion type, description, completion conditions, type-specific target/milestone definition, author, approval state, generation model/prompt version where AI-generated, and creation time. Validate the structured definition with typed Pydantic models before persistence. |
| `goal_assessment_runs` | One user-triggered single-goal or bounded multi-goal analysis run, with trigger, lifecycle (`PENDING`/`RUNNING`/`COMPLETED`/`PARTIAL`/`FAILED`), timestamps, model/prompt/configuration versions, and sanitized failure/usage metadata. Use a tracked job only if the measured runtime requires asynchronous execution. |
| `goal_criterion_assessments` | Immutable assessment result for one exact criterion version and run: result status, rationale, confidence, assessment time, model/prompt/configuration versions, input fingerprint, and invalidation metadata. Do not persist AI-authored progress as authoritative; store only validated measurements needed by deterministic formulas. |
| `goal_criterion_assessment_evidence` | Evidence mappings used by an assessment, with the referenced evidence version when available and the evidence-review/source-validity state observed at assessment time. Reference the goal's existing `evidence_mappings`, preserving optional milestone association. |
| `goal_criterion_assessment_events` | Append-only lifecycle and decision history: `CURRENT`/`STALE`/`OBSOLETE` transitions, employee confirmation/correction/challenge, actor, timestamp, and reason. Do not overwrite the AI result when a person responds. |

Use database constraints for unique `(criterion_id, version)`, valid foreign
keys, and indexes for current assessments by goal/criterion and run. Enforce
ownership through the goal relationship and service authorization. Retiring a
criterion must preserve versions and assessment history. Persist structured
assessment results and run provenance, not full prompt contents or sensitive
retrieved documents by default.

### Source freshness

Use existing `evidence.content_hash`, `source_updated_at`, and
`evidence_versions` as the first source-version signals. Persist the exact
evidence version or content fingerprint used by each assessment. Record last
verification time and accessibility for external links; if existing connector
flows cannot persist these facts, add a small source-check record keyed to the
evidence item rather than placing transient fetch errors in assessment output.
A temporary retrieval failure must produce an explicit limitation/review
state, not a claim that the achievement is invalid.

Normalize source results into the existing evidence model where possible,
retaining canonical source ID/URL, source type, title/excerpt, contributor
metadata when the source supplies it, source timestamps/version, retrieval
time, accessibility, and criterion associations. Store only content allowed
by source permissions and retention policy.

## 4. Backend services, API, and model handling

### Criteria

- Add typed request/response models for binary outcomes, milestone-based
  outcomes, and measurable targets.
- Add a goal-scoped generation operation that stores proposals as unapproved
  versions. Generation failure must not create criteria or report success.
- Support list, edit/version, approve, and retire operations. A material change
  to scope, conditions, target, milestones, or weights creates a new version;
  it never edits the definition referenced by a prior assessment.
- Require employee approval before a proposed criterion becomes the current
  approved definition used for finalized summaries.

### Assessment

- Add a goal-scoped assess/reassess operation and a read operation for the
  current summary and assessment history. Evolve the existing
  `GET /goals/{goal_id}/assessment` contract in coordination with both web
  consumers; there must be one assessment/aggregation source of truth, not a
  parallel legacy score.
- Provide a bounded Analyze Goals operation that returns or creates a tracked
  `goal_assessment_runs` record with per-goal outcomes. Support partial
  success; use asynchronous job handling only if measured latency warrants it.
- AI evaluates submitted evidence independently of manager acceptance. Include
  evidence review state, source validity, and limitations in the result; never
  label an AI conclusion as manager-verified solely because confidence is high.
- Reuse authorized retrieval and existing LLM abstractions. Treat model output
  as untrusted: validate schema, criterion IDs, evidence/mapping IDs, goal
  ownership, citations, enum values, numeric ranges, and that citations refer
  only to input evidence. Reject invalid output explicitly.
- Persist the model/prompt/configuration version and the exact criterion and
  evidence versions/fingerprint used. Persist errors as explicit failed or
  unavailable states only where the product needs history; do not turn
  provider failures into empty or successful assessments.
- Employee confirmation is optional. Record confirmations, corrections, and
  challenges as events linked to the original AI assessment. Rejected or
  needs-information evidence retains its review label in the UI and citations.

### LLM roles, prompts, and retrieval orchestration

Use the responsibility boundary **LLM reasons; retrieval adapters retrieve;
backend validates and calculates; database preserves the source of truth**.
The LLM never authorizes a user, executes arbitrary tools, writes directly to
the database, or supplies authoritative progress calculations.

Implement one auditable workflow using the existing LLM abstraction and
services; split code by stable responsibilities only where it improves
validation and testing. Build each model request from a context builder that
includes only relevant, authorized, current goal data, approved criterion
versions, evidence content/metadata, and necessary prior history. Prior
assessments are context, not a default answer to repeat.
Persist authoritative product state in the database; use task-specific retrieved
context rather than adding a separate conversational-memory engine.

Add version-controlled prompt templates and typed input/output schemas,
following repository conventions. If no existing conventions are present, use
versioned prompt files under `ai/prompts/` and typed schemas under
`ai/schemas/`. The role-and-prompts reference defines the proposed tasks:

| Prompt/task | Responsibility and required output |
|---|---|
| A — Criteria generation | Propose clear, non-duplicative criteria, types, completion definitions, evidence suggestions, and clarifications. Output is unapproved until the employee approves it. |
| B — Evidence discovery plan | Propose targeted searches tied to criterion IDs and information needs; application code validates source/tool names, arguments, permissions, and budgets before execution. |
| C — Retrieval sufficiency | Identify missing information and whether a bounded follow-up search is worthwhile; include a stop reason and never claim exhaustive search without retrieval evidence. |
| D — Evidence interpretation | Separate source facts, inferences, contradictions, excerpts, and limitations while preserving provenance; do not infer an individual's contribution from team output alone. |
| E — Evidence matching | Return criterion/version and evidence references, relationship type (direct, indirect, contradictory, irrelevant), support/gaps, rationale, and uncertainty. |
| F — Criterion assessment | Propose only `NOT_STARTED`, `IN_PROGRESS`, `MET`, or `NEEDS_REVIEW`, with evidence references, rationale, unmet conditions, and uncertainty. `NOT_ASSESSED` is a backend state when no result exists. Missing evidence alone is not proof of `NOT_STARTED`; the model must not authoritatively calculate progress or claim to persist a result. |
| G — Goal summary (optional) | Summarize only the backend-validated current snapshot, gaps, limitations, and next actions; do not reassess criteria or recalculate progress. |

Validate every response against typed schemas and the exact request context.
Unknown source/tool names, IDs not present in the authorized request, invalid
citations, and malformed outputs fail explicitly. Store prompt/template version
along with model and configuration version on each run/assessment. Add prompt
contract tests and evaluation cases for each task. Do not assume a `SKILL.md`
file is executed automatically; add skill files only if an application runtime
explicitly loads and applies them.

### Evidence discovery and MCP/connector boundary

- **Implemented first slice:** reanalysis reuses the existing authorized
  GitHub/Jira discovery pipeline. Source requests are bounded, discoveries are
  attached to the goal without duplicates, new mappings remain pending review,
  changed source content appends an evidence version, and per-provider errors
  are surfaced on the run while other providers and stored evidence continue.
  Search terms are deterministically derived from approved criterion
  definitions and combined into bounded provider queries. The source-summary
  prompt identifies criterion matches and reports per-criterion retrieval
  sufficiency; it does not generate a separate search plan or perform
  iterative follow-up searches.
- First audit tool/connector capabilities, argument schemas, pagination,
  returned metadata, scopes, and per-user permissions. The current first-party
  connectors are GitHub and Jira; use their existing authorized search/retrieval
  paths unless the audit confirms an available MCP adapter is required.
- Do not claim Confluence support or build new connectors without a concrete
  M6.6 use case and confirmed API/tool capability.
- For future search-plan refinement, application code must execute only
  allowlisted operations for connected sources and the user's authorized
  scope. Include manually submitted and already stored evidence in the same
  source-neutral input model.
- Normalize and deduplicate results. Preserve canonical source ID/URL, source
  type, title/excerpt, contributor metadata when supplied, created/updated
  timestamps, source version/fingerprint, retrieval time, accessibility, and
  associated criterion IDs where available. Respect source and retention
  policies for stored content.
- Handle pagination, bounded retries, rate limits, result count, latency, and
  cost budgets. Fetch full content only when authorized and needed. Record
  retrieval failures separately from conclusions.
- After initial retrieval, allow only bounded follow-up searches when they can
  address a specific criterion gap. Stop at budget limits or when further
  retrieval is unlikely to help. Never represent incomplete retrieval as
  exhaustive.
- Treat GitHub PR text, Jira comments, documents, and all retrieved content as
  untrusted data, not instructions. Prompt-injection content cannot expand
  tool access, change criteria, bypass authorization, expose secrets, or
  alter persisted results.

### Assessment states

Keep criterion outcome separate from result freshness:

- Result: `NOT_ASSESSED`, `NOT_STARTED`, `IN_PROGRESS`, `MET`, `NEEDS_REVIEW`.
- Lifecycle: `CURRENT`, `STALE`, `OBSOLETE`.

The latest result for the current approved criterion version and unchanged
inputs is `CURRENT`. A material source/input change makes the affected result
`STALE`. A changed criterion version or a newer assessment superseding an older
one makes the older result `OBSOLETE`. Only current-version, current-lifecycle
results contribute to current goal summaries. Before reassessment completes,
the UI shows pending/unavailable rather than presenting an obsolete result as
current.

### Deterministic progress

- Binary: `0%` or `100%` based on explicit completion conditions.
- Milestone-based: completed milestone weights divided by total milestone
  weights; equal weights initially.
- Measurable target: for explicitly defined increasing targets, calculate
  measured progress relative to the target and cap at `100%`. Require an
  explicit formula for other directions.
- Equal criterion weights by default. Validate definitions before assessment;
  do not infer a formula for unsupported or ambiguous criteria.
- Return separate fields for criteria met/count/percentage, calculated goal
  progress, evidence coverage, and AI confidence. Never use confidence as
  progress or proof of achievement.

## 5. Frontend changes

### Goal creation and editing

- Add an AI-propose-criteria action after the goal has been saved, so the
  proposal is associated with a stable goal ID.
- Show generated criteria as editable, unapproved proposals. Allow employees
  to add, edit, remove, and approve criteria before they drive assessment.
- Provide type-specific fields and validation for completion conditions,
  milestone definitions, and measurable targets. Explain when the goal is too
  ambiguous and needs clarification.

### Goal detail

- Replace the fixed “expected achievement count” card with criterion-level
  results and a deterministic summary.
- Show evidence linked to each criterion, source citations, rationale,
  uncertainty, AI confidence, review state, source-validity/last-verified
  details, and assessment timestamp.
- Let employees confirm, correct, challenge, and request reassessment without
  overwriting the AI result.
- Show version history, stale/obsolete/pending states, provider failures,
  source-access limitations, and recoverable retry actions.
- Keep lifecycle actions and evidence approval UI behavior unchanged.

### Goals page

- Render the same backend summary and formulas as Goal detail; do not recreate
  progress arithmetic in React.
- Show goal progress, criteria met, evidence coverage, and status separately.
- Add an Analyze Goals action for eligible user-owned goals, with run progress,
  per-goal completion/failure, and explicit retry for recoverable failures.
- Use a batch summary endpoint or existing goals response expansion if the
  current per-goal assessment requests become an N+1 bottleneck.
- Invalidate/refetch summaries after criteria, evidence, source checks, user
  decisions, or reassessment change.

## 6. Implementation sequence and deliverables

1. **Baseline and contracts**
   - Confirm existing goal/evidence retrieval, GitHub/Jira connector
     capabilities, source permissions, prompt conventions, and service test
     fixtures. Confirm whether an MCP adapter is actually available before
     adding one.
   - Define Pydantic request/response types, type-specific criterion schema,
     assessment response, and API error behavior.
   - Define the input fingerprint fields and exact result/lifecycle transition
     rules. Define prompt task inputs/outputs, versions, limits, and failure
     behavior.
2. **Persistence**
   - Add migration and SQLAlchemy models/repositories for criteria, versions,
     assessments, assessment evidence, and append-only events.
   - Add repository integration tests, ownership constraints, and history
     preservation tests.
3. **Criteria workflow**
   - Implement Prompt A using the existing LLM interface and version-controlled
     template/schema. Preserve proposals as unapproved until employee action.
   - Add create/edit/version/approve/retire services and goal-scoped routes.
   - Test invalid model output, ambiguous goals, duplicate/invalid criterion
     IDs, authorization, prompt regressions, and edits retaining prior
     versions.
4. **Assessment and aggregation**
   - **Implemented:** bounded authorized GitHub/Jira source refresh on
     reanalysis, with query terms derived from each approved criterion.
     Candidate summaries identify the criteria each source record relates to
     and report retrieval sufficiency; only matched newly discovered records
     are passed to that criterion's assessment, while previously attached
     evidence remains eligible for every criterion. Source-specific failures
     produce partial run results.
   - Keep interpretation, evidence matching, and criterion assessment in the
     current validated assessment prompt; separate prompt calls are not
     required for this implementation.
   - Implement citation/input validation, immutable result persistence,
     evidence-review-state snapshots, freshness fingerprints, and append-only
     employee decision events.
   - Implement deterministic progress and summary calculations for the three
     criterion types. Treat any AI-extracted measurement as untrusted input;
     validate its evidence reference before deterministic calculation.
   - Replace the fixed-three legacy assessment calculation; coordinate the
     response change with all API consumers.
5. **Goal detail and Goals UI**
   - **Implemented first slice:** criteria proposal/review/approval and
     criterion assessment components consume shared API summaries; the
     reanalysis action shows source-refresh progress and partial-source errors.
   - **Implemented E2E slice:** one employee journey covers goal creation,
     criteria generation/edit/approval, evidence attachment, assessment
     citations, stale input, and reanalysis refresh. Additional tests cover
     employee feedback, manager evidence decisions, insufficient/contradictory
     evidence, obsolete history, loading/empty states, and reanalysis recovery.
   - Continue validating source-access limitations and query-load retry states
     across API consumers.
6. **Freshness and quality**
   - **Implemented first slice:** reanalysis re-fetches connected sources and
     per-goal/per-provider checkpoints limit repeat retrieval and
     summarization; fingerprints/version history expose changed inputs. The
     incremental query overlaps one calendar day and applies an exact
     candidate-timestamp cutoff. Checkpoints advance independently only after
     successful source persistence.
   - Background event/scheduled freshness checks and reanalysis without a user
     request are out of scope. Last-verified metadata and display remain open
     UX work; source refresh currently occurs during user-triggered reanalysis.
   - Build a human-reviewed evaluation dataset and measure matching precision
     and recall, human agreement, citation validity, unsupported claims,
     retrieval quality, source invalidation reliability, and repeatability for
     each prompt task.
   - Set numeric release thresholds from that dataset before production;
     support abstention when evidence is insufficient. Track prompt/model
     versions, latency, provider/retrieval failures, token use, and cost while
     avoiding unnecessary logging of sensitive source content.
7. **Integrated validation**
   - Run migration, backend unit/integration, frontend unit, API contract, and
     Playwright coverage.
   - Verify detail/list parity, owner isolation, manager-review distinctions,
     failure behavior, version history, and no change to goal lifecycle.
   - Record commands, environment, evaluation results, and unresolved limits
     before marking M6.6 complete.

## 7. Required test coverage

- **Schema/repository:** version uniqueness, immutable history, evidence
  mapping/version links, cascade/retirement behavior, and owner scoping.
- **Criteria service/API:** generation output validation, user edits,
  approval, material vs non-material edits, reassessment on new versions,
  goal ownership, and clarification for ambiguous goals.
- **Assessment service:** submitted evidence at every review state; inaccessible,
  ambiguous, and contradictory sources; invalid/malicious model references;
  low confidence/abstention; provider timeout and malformed response.
- **Prompt contracts:** schema tests and adversarial fixtures for criteria
  generation, unknown search tools/sources, retrieval sufficiency, evidence
  interpretation, many-to-many matching, assessment abstention, and summary
  generation that must not change statuses or arithmetic.
- **Retrieval:** authorization and connector scope, pagination, deduplication,
  rate/timeout/result budgets, partial failures, unsupported tools, source
  version metadata, and prompt-injection text in retrieved content.
- **Progress:** binary 0/100; equal milestone weights; measurable increasing
  targets and cap; explicit rejection of unsupported formulas; equal criterion
  weights; distinct criteria-met, progress, coverage, and confidence values.
- **Freshness/history:** changed hashes/source versions, inaccessible external
  links, temporary connector failures, criterion edits, reanalysis, prompt/model
  version changes, stale-to-obsolete transitions, and preserved prior results.
- **Authorization:** cross-user goal/evidence/criterion/assessment IDs are
  rejected; the model cannot introduce IDs outside the authorized request.
- **Frontend/E2E:** mock-backed tests cover create goal →
  generate/edit/approve criteria → add evidence → assess and inspect citation
  → change input → observe stale state → reassess; employee feedback, manager
  review decisions, insufficient/contradictory evidence, obsolete history,
  loading/empty states, and failure recovery. Detail/Goals parity and
  completed/partial/failed run displays also have coverage. Query-load retry
  and source-access limitation states remain open.
- **AI evaluation:** use a human-reviewed dataset and report each agreed
  quality metric per prompt task, including retrieval quality and citation
  grounding; no production release until numeric thresholds are set and met.

## 8. Out of scope

- Separate monthly/quarterly/yearly Impact Analysis (M6.7); it consumes
  validated assessments and does not edit criterion-level records.
- 1:1 briefs and career reports (M6.8).
- Autonomous performance ratings, promotion decisions, or treating generated
  criteria/suggestions as achievements.
- New external connectors, broad orchestration, or a separate scoring system
  unless needed to satisfy an approved M6.6 requirement.

## 9. Completion gate

M6.6 is complete only when an employee can create a goal, review and approve
versioned AI-proposed criteria, submit supported evidence, inspect source-linked
assessments, and see consistent deterministic results on Goal detail and Goals.
The system must distinguish AI assessment, employee decisions, and manager
review; preserve immutable history; mark stale/obsolete results correctly;
enforce authorization; pass backend/UI/integration/E2E tests; and meet numeric
AI-quality thresholds established on a representative human-reviewed dataset.
