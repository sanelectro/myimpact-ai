# Goal Validation v1 — Copilot Implementation Guide

**Dataset:** `goal-validation-v1`  
**Dataset version:** `1.0.0`  
**Rubric:** `goal-validation-rubric-v1`  
**Cases:** 30  
**Current state:** Draft, AI suggestions proposed, human ground truth not approved

## 1. Purpose

This document accompanies `goal-validation-v1-final.json`. The JSON is the canonical starter benchmark representation for evaluating whether employee goals are sufficiently clear, attributable, measurable, feasible and aligned with role expectations before they proceed through the goal approval and activation workflow.

The 30 cases preserve the supplied case IDs, names, goal descriptions, goal types and six benchmark categories. AI labels and rationales are initial proposals based on the supplied case text, not human-approved answers.

## 2. Critical status distinctions

Do not conflate these separate concepts:

- **Goal validation label:** `READY`, `NEEDS_IMPROVEMENT`, `NEEDS_REVIEW`, or `INVALID`.
- **Goal approval status:** whether the manager or authorized approver has approved the goal.
- **Goal lifecycle status:** whether the goal is draft, active, completed, etc.
- **Benchmark review status:** whether human reviewers have reviewed a benchmark case.
- **Benchmark reference approval:** whether the human-adjudicated reference answer has been approved.

`READY` does not mean `APPROVED` or `ACTIVE`. It means the goal is sufficiently well-defined to proceed to the applicable approval workflow.

## 3. Validation labels

| Label | Meaning |
|---|---|
| `READY` | The goal is sufficiently clear and assessable to proceed to the applicable approval workflow. |
| `NEEDS_IMPROVEMENT` | Specific clarification or refinement is needed; the employee can usually address it. |
| `NEEDS_REVIEW` | A human or authoritative contextual decision is needed before a reliable decision can be made. |
| `INVALID` | The goal violates an explicit policy or has a fundamental issue not resolvable through ordinary clarification. |

Do not use `INVALID` merely because a goal is vague, ambitious, missing context, or difficult to measure. Use `NEEDS_REVIEW` when authoritative context is missing or conflicting.

## 4. Dataset structure

Each case contains:

1. `case_id`, `case_version`, category, dimensions and polarity.
2. `goal`: the goal statement and structured goal attributes.
3. `context`: employee role, role expectations and organizational/source context available to the evaluator.
4. `ai_suggestion`: proposed label, rationale, findings, missing information, questions and improvements.
5. `human_review`: assignments, independent reviews, comparison and resolution.
6. `reference`: the final human-approved benchmark answer, intentionally empty initially.
7. `metadata`: source and maintenance information.

### AI suggestion fields

- `suggested_label`: AI's proposed goal-validation label.
- `rationale`: concise explanation supporting the label.
- `identified_findings`: dimension-specific observations with severity and recommendation.
- `missing_information`: information required to validate the goal reliably.
- `suggested_questions`: questions to ask the employee or goal owner.
- `suggested_improvements`: actionable refinements.
- `model_reference`, `prompt_version`, `evaluation_run_id`, `generated_at`: provenance fields to populate when an actual model run is performed.
- `suggestion_status`: remains `PROPOSED_NOT_HUMAN_APPROVED` until governed by the review process.

## 5. Human review and reference rules

- Human reviewers must independently assess the case without seeing the AI suggestion before submitting their initial review.
- Store each human submission separately; do not overwrite a previous review.
- Use the configured dual-review and adjudication workflow.
- Populate `reference` only after the required review/adjudication and explicit approval process.
- Do not copy `ai_suggestion.suggested_label` into `reference.reference_label` automatically.
- Keep reviewer identity, timestamps, rationale and audit history in the existing review workflow.
- The JSON is a benchmark interchange/seed structure. It does not require one database table per nested JSON object.

## 6. Evaluation and contextual fairness

- AI and human reviewers must receive the same goal and contextual evidence.
- Do not invent employee role, authority, target source, baseline, deadline or organizational policy.
- If required context is absent, surface it explicitly and prefer `NEEDS_REVIEW` where the decision depends on that context.
- Missing contribution detail is not evidence that the employee failed to contribute.
- Distinguish an employee's delivery responsibility from wider business outcomes outside their control.
- A delivery goal can be `READY` without a business-impact target when the deliverable and acceptance criteria are clear.
- Do not impose numerical targets on every goal by default.
- Do not judge feasibility from wording alone when team capacity, approved plans, scope or dependencies are unknown.

## 7. Case coverage

The 30 cases cover the six supplied categories:

1. `CLARITY_AND_STRUCTURE`
2. `OWNERSHIP_AND_ACCOUNTABILITY`
3. `DELIVERY_OUTCOME_IMPACT`
4. `SMART_AND_MEASURABILITY`
5. `FEASIBILITY_AND_ROLE_ALIGNMENT`
6. `CONFLICTING_AND_INCOMPLETE`

The initial AI suggestions are intentionally not treated as a balanced or approved gold dataset. In particular, the current set has very few positive cases and no `INVALID` example. Expand the dataset with additional positive, negative and borderline cases before using it for release-gating thresholds.

## 8. Implementation instructions for Copilot

### Phase 0 — inspect only

Inspect all existing repositories and report findings before changing code:

- `myimpact-web`
- `myimpact-api`
- `myimpact-ai`
- `myimpact-db`

Locate the existing benchmark dataset loader/schema, evaluation runner, prompt/rubric versioning, human-review workflow, review tables/models/services, API contracts and frontend review screens.

Do not assume the proposed JSON maps one-to-one to database tables. Reuse the existing M6.6 review infrastructure wherever possible. Identify schema and naming conventions, existing enums, migration patterns and current API behavior.

**Do not edit files, generate migrations, or change runtime behavior during this inspection phase.** Return a repository-by-repository gap analysis and proposed minimal change plan for approval.

### Phase 1 — after explicit approval

1. Add support for the goal-validation dataset and its schema using existing benchmark conventions.
2. Preserve the original 30 case inputs and case IDs.
3. Store AI suggestions separately from human reviews and approved reference answers.
4. Capture prompt, rubric, model and evaluation-run provenance.
5. Integrate with existing independent review, comparison and adjudication workflow.
6. Add schema validation and tests for missing context, invalid labels, duplicate case IDs, case versioning and separation of AI/human/reference data.
7. Keep changes scoped to Goal Validation; do not regress M6.6 Evidence Assessment.
8. Use Flyway for database changes. Never edit already-applied migration files; add a new migration if a schema change is approved.
9. Preserve existing records and APIs. Provide backward-compatible migration and rollout considerations.
10. Run focused tests and the relevant integrated backend, AI, frontend, API-contract and migration validation.

## 9. Required safeguards

- No AI suggestion may be presented as human-approved ground truth.
- No benchmark case may be marked approved solely because AI generated a label.
- No automatic goal rewrite or invented target/ownership.
- No silent mutation of a case after reviews have been submitted; create a new case version.
- No unrelated refactoring or replacement of the existing review subsystem.
- No production release threshold should be inferred from this starter dataset.
