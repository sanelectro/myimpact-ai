# M6.6 Criterion Assessment Evaluation Dataset — Status

## Summary

A starter evaluation dataset, repeatable assessment runner, metrics, and dataset-driven tests are in place. The eligibility gate is hardened, but the dataset is **not approved as human-reviewed ground truth**, and numeric release thresholds have **not** been approved. The current scores are exploratory only and must not be used as a release pass.

## Completed

- Created [`m66_criterion_assessment.json`](../../evaluation/m66_criterion_assessment.json) with six representative cases:
  - Supported completion with unrelated evidence present.
  - Partial progress.
  - Contradictory sources.
  - Topically similar but irrelevant evidence.
  - No evidence.
  - Team outcome without evidence of individual contribution.
- Each case includes a goal, criterion definition, evidence candidates and mapping IDs, retrieval and assessment sufficiency labels, expected outcome, expected evidence relationships, expected citations, and reference rationale.
- Recorded review and threshold state explicitly:
  - Dataset label status: `DRAFT_UNREVIEWED`.
  - Human review status: `PENDING`; no reviewers or approval date recorded.
  - Threshold approval status: `NOT_APPROVED`; threshold values are null.
- Added [`app/evaluation/m66.py`](../../app/evaluation/m66.py) to run the production criterion-assessment prompt, validate the structured output and citations, and calculate run-level metrics.
- Added [`app/evaluation/m66_eligibility.py`](../../app/evaluation/m66_eligibility.py) with deterministic eligibility validation and machine-readable reasons. It checks human review/adjudication, threshold approval and numeric ranges, required dataset/case/repeat declarations, matching prompt/model versions, valid unique results/citations, run completeness, and metric thresholds.
- Added [`scripts/evaluate_m66_criterion_assessment.py`](../../scripts/evaluate_m66_criterion_assessment.py) to run the configured LLM against each case repeatedly and print a JSON report. It does not persist assessments.
- Reused the shared dataset in unit and integration tests, and in the M66 Playwright contradiction scenario.
- Documented evaluation usage in the [AI service README](../../README.md).

The unsupported-assessment-claim metric is currently an **outcome-level proxy**. It detects achievement predictions that conflict with the reference outcome or lack a reference supporting citation; it does not verify every factual statement in a generated rationale.

## Work needed before release use

### 1. Human-review the examples

- Agree on a written annotation guide covering evidence relevance, support versus contradiction, sufficiency, attribution, expected result, and citation selection.
- Have at least two reviewers label cases independently; record reviewer identities, review dates, disagreements, adjudication outcomes, and rationale.
- Review the partial-rollout disagreement first, and refine the case or labels only after reviewers resolve the intended interpretation.
- Mark the dataset `HUMAN_REVIEWED` only after the review has actually happened. Do not populate reviewer fields with placeholders.

### 2. Expand and maintain the benchmark

- Six cases are a useful starter set, but are too few to represent release behavior across evidence sources and edge cases.
- Add reviewed examples for temporal/stale evidence, measurable targets, milestone completion, weak or conflicting sources, missing measurements, employee attribution, and multiple relevant/irrelevant candidates.
- Keep a versioned holdout set that is not used to tune prompts or thresholds. Track the dataset version alongside prompt and model versions.

### 3. Agree and record numeric thresholds

- First confirm metric definitions and denominators with the team, especially how repeated runs and unsupported claims are counted.
- Use reviewed pilot results and the product's risk tolerance to set the targets. Record the approvers, approval date, rationale, and threshold values; do not infer approval from non-null numbers.
- No numeric threshold is proposed or approved in this document.

### 4. Maintain the release eligibility gate

The gate now checks the approval and version metadata, validates threshold values and comparisons, and requires one successful, valid result for every declared case/repeat slot. Preserve these checks when changing the dataset or runner. The real dataset remains ineligible until:

- Reviewers complete and record adjudication, then approve the exact dataset version.
- The team approves thresholds, approvers, and approval date.
- The approved model version is declared and matches the model used for all runs.
- Complete, successful runs meet the team-approved metric thresholds.

### 5. Improve quality measurement

- Add human-reviewed rationale/claim annotations or a separate claim-level audit before interpreting the unsupported-claim metric as factuality coverage.
- Keep reporting outcome agreement, citation mapping, and abstention separately; do not collapse them into one score.
- Review per-case and per-scenario results alongside aggregate metrics. Repeatability should be assessed for outcomes and citations, and can be extended to rationale consistency if the team defines a reliable scoring method.

## How to run

From the `myimpact-ai` directory, with the AI service's LLM settings configured:

```bash
python -m scripts.evaluate_m66_criterion_assessment --repeats 3
```

The runner reports `release_quality_eligible: false` for this dataset, with reasons for every unmet approval, version, threshold, or run requirement. This is expected until genuine human review and team threshold approval are recorded and a complete eligible run meets the approved gates.
