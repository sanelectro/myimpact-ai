## 0. Current development design

### 0.1 Product behavior and scope

For an employee-owned active parent G1, creating G1 v2 must create a Draft version of **every** descendant, deactivate the old active hierarchy, and hold pending old-version evidence reviews in one atomic operation. This includes descendants that were already inactive or completed: their old state and history remain intact. Each descendant draft starts from its own latest product-visible version, even if inactive or unapproved. No goal, milestone, evidence approval, completion or score transfers to the new versions.

There may be **no active version** while the new version is Draft or approved. A manager formally approves each new goal definition and every included milestone; the employee then activates each goal separately, parent-first. Only after activation can the employee select historical evidence for reuse and request a fresh manager decision. The old evidence remains linked to its historical version.

The employee can discard a parent draft or deactivate the new parent hierarchy. This does not automatically reactivate the old hierarchy. If the employee explicitly reactivates the old parent, restore only the descendants that were active before the relevant deactivation, parent-first and atomically. Completed descendants stay completed; previously inactive descendants stay inactive. Existing approvals and milestone completion remain associated with the same old version; previously pending evidence reviews require new requests.

**Example:** G1 v1 has G1.1 v1, a completed quarterly goal. Creating G1 v2 makes G1.1's next version a Draft, showing its previous status and details. Following fresh goal and included-milestone approvals, the employee may activate the child version after G1 v2 is active; old completion does not transfer. G1.1 v1 remains completed in history.

**Boundary:** A genuinely different commitment can be a new goal ID. Exactly where to draw that boundary against a revised completed child remains open. Adhoc and Stretch may group unparented work without artificial monthly parents. Roadmap month- and quarter-end are reporting checkpoints by default, not automatic hard date barriers.

### 0.2 Current implementation, not target behavior

- The existing UI and authenticated proposal API prepare, preview and validate a title/description/date proposal while **leaving the live goal unchanged**. They do not implement immediate deactivation, hierarchy-wide drafting, manager approval or activation. The existing direct Edit path still mutates the live goal. Changed milestone proposals cannot yet be validated by the existing proposal validator.
- Snapshots, an operative-version pointer, proposal heads, receipts, baseline observations, some goal/criterion/milestone writer locks and hierarchy date-preview infrastructure exist. Existing normal readers still use latest `STANDARD` semantics rather than the pointer. Existing evidence/assessment context and deletion behavior do not guarantee version-specific review or retained history.
- The current date preview compares known parent and child boundaries. It does **not** implement the newer distinction between planning checkpoints, sprint windows and explicit hard deadlines.
- Existing local and disposable test results described in section 10 verify prior slices only. They are not acceptance evidence for the revised workflow. Preserve existing behavior behind the feature gate while the new contracts are implemented.

### 0.3 Candidate model and invariants

These are design requirements, not a claim that the schema or APIs already support them. Review the existing schema, migration ordering and compatibility before choosing concrete columns or tables.

| Concern | Required representation or invariant |
|---|---|
| Identity and selection | Keep stable employee-owned goal IDs. At most one active definition per goal; an explicit no-active-version state is valid. Readers must not substitute a latest Draft or an old version. Investigate how to distinguish no active version from legacy/uninitialized pointer nulls before cutover. |
| Definition and status | Preserve immutable versioned definition snapshots; separately represent draft, approval, activation/deactivation and completed execution without overwriting historical content. A completed old version remains completed when a later draft exists. |
| Source and hierarchy | Record the source version for every generated child draft and the parent/child version context of the revision operation. Resolve the latest **product-visible** version; technical `OBSERVED` baselines must not accidentally be chosen merely because they have a higher allocated number. Define an explicit safe policy for ambiguous legacy records. |
| Deactivation and restoration | Record exactly which old versions were active at deactivation, their hierarchy and restoration lineage. Keep independently inactive or completed descendants out of automatic active restoration. A conflict must not silently overwrite later work or produce partial restoration. |
| Manager decisions | Bind each goal and milestone approval to its exact reviewed definition and authorized manager. Grouped reapproval is explicit for selected previously approved, unchanged goals and milestones only, with a fresh decision per selected item and all-or-nothing batch semantics. Changed items require individual review. |
| Evidence and assessments | Bind evidence review and assessment context to the exact goal definition and reviewed inputs. Old approvals and assessments stay historical. Pending old reviews are held on deactivation, rejected at submission while held, and closed as superseded on activation of the replacement. Previously pending reviews need new requests after restoration. |
| Dates and completion | Preserve each version's prior dates and show them below the corresponding new-version fields. The employee decides new values; field defaults are open. Actual dates must not make a new version complete by themselves. An explicit Mark complete action records a server-side completion transition for the exact version; checkpoint reporting uses the recorded transition, not a backdated actual end date. Exact date storage and reporting cutoffs remain design work. |
| History and retention | Preserve old snapshots, hierarchy, milestones, review decisions, completion and assessment context. Do not erase history through ordinary deletion, cascade paths or reactivation. For legacy inputs whose approval or effectivity cannot be proved, show unknown rather than inventing history. |

### 0.4 First implementation slice: atomic hierarchy revision

**Goal:** Build and test a transaction-neutral backend coordinator for creating a revision group. This slice is not permission to expose the new workflow to users before its safety dependencies are complete.

1. Authenticate the owner; capture the intended root, expected hierarchy and source revisions, and an idempotency key. Detect unsupported or ambiguous legacy state explicitly rather than guessing.
2. In a PostgreSQL READ COMMITTED transaction, take the existing hierarchy advisory lock in its required separate statement. Then take the command idempotency lock and affected goal/resource locks in a documented deterministic order compatible with all participating writers. No provider or LLM calls while locks are held.
3. Re-read the hierarchy and all latest product-visible sources under the locks. Detect changes since review, missing definitions, incompatible concurrent drafts, ownership violations or unsupported states; return an explicit conflict and make no changes. The precise treatment of pre-existing child drafts needs review; never overwrite them.
4. Capture the old active hierarchy and source provenance; stage the root draft and a new draft for every descendant using that descendant's latest source. Preserve existing completed/inactive state and prior history. The employee can later review and modify draft content; no prior approval, evidence applicability, completion or score is inherited.
5. In the **same transaction**, deactivate the old active versions and their current milestone context, establish holds for pending evidence reviews, record revision-group/restoration lineage and audit events, and persist the success receipt. Leave the new drafts inactive. Commit once; return success only after commit. A failed stage or commit rolls back the entire operation.
6. Require same-key/same-payload retries to return the committed result; a different payload under the same key conflicts. Detect concurrent source, hierarchy, review and lifecycle changes using the shared locking/recheck protocol; include the evidence decision submission path so a stale manager page cannot bypass the hold.

Existing service helpers that commit independently cannot be used inside this coordinator without transaction-neutral alternatives. Existing prepared-proposal savepoints do not replace the outer atomic transaction: `Session.begin_nested()` flushes prior pending state before its savepoint, and the owner must roll back the entire outer transaction on any batch failure. Preserve the existing single-goal path until a safe migration/gating strategy is agreed; do not silently repurpose it.

**Safety gate:** A test-only internal coordinator is not a user-visible completed feature. Do not allow the operation through UI/API until evidence holds are enforced on the manager submission path, historical context is retained, no-active-version readers and relevant writers are consistent, and authorization and concurrency are verified. No partial deactivation or direct-edit bypass may be presented as the new workflow.

### 0.5 Dependent workflow after the foundation

1. **Review and approval:** Show old version details and the exact new definitions. Validate the candidate and obtain formal manager goal and per-milestone approvals. Group selected previously approved unchanged goals and milestones only; record each fresh decision atomically. Resolve how goal edits invalidate related approvals before implementation.
2. **Separate activation:** Check exact current validation and approvals, current parent activation, scheduling rules, and the absence of another active version under locks. Commit selection, projection, pending-review supersession and audit together. Failure leaves the previous hierarchy inactive; it does not undo an earlier successful creation.
3. **Goal History and evidence:** Expose prior definitions, milestone state, evidence decisions and assessments without mutation. After the new version is active, link chosen evidence by reference and require fresh manager review. Do not count it before that approval. Pin review to the actual evidence content reviewed; the content-change policy remains open.
4. **Discard, deactivation and restoration:** Deactivate the new hierarchy without deleting it. Explicitly reactivate the old hierarchy parent-first as one atomic operation, using the recorded old active set. Retain the old versions' own approvals and milestone completion; require new requests for previously pending evidence. Define independently changed-child conflict resolution before release.
5. **Dates and reporting:** Add version-distinguishable date handling and explicit completion transitions. Preserve original Roadmap parent and report carryover without duplicate credit; calendar month/quarter/year checkpoints use recorded completion time. Time zone, field defaults, hard-deadline policy and inactive-version reporting remain open.

### 0.6 Acceptance and release gates

Add focused unit and disposable PostgreSQL integration tests for the first slice; use authenticated API/UI tests only when those surfaces are built. At minimum verify:

- A root with active, inactive and completed descendants creates a draft for **every** descendant from its latest eligible product-visible source, including a later unapproved draft. Old completed versions stay completed; sources and old active membership are recorded.
- A failure at each staged step, including an evidence-hold write or commit, leaves the entire pre-command hierarchy and all reviews unchanged. A retry returns the original receipt; conflicting key reuse fails.
- Concurrent hierarchy/source changes and a manager decision racing v2 creation serialize to a coherent outcome: either the old decision commits before deactivation and remains historical, or submission is blocked after the hold. No partial drafts, lost updates or decisions attributed to the wrong version.
- Current reads and all relevant writers consistently handle an explicitly inactive goal without falling back to v1 or showing a Draft as active. Legacy and direct writers cannot bypass the protected transition.
- Later workflow tests cover exact goal/milestone approvals and grouped unchanged-only atomicity; parent-first activation; post-activation evidence reapproval; history retention; discard and atomic restoration; completed-child history; explicit completion, reporting cutoffs and corrections.

**Open before affected implementation:** date field defaults; goal-edit approval invalidation; definition equality and source approval for grouped review; restoration conflicts; boundary between revised completed work and a new commitment; evidence-content revision policy; technical/legacy source resolution; cutoff time zone, reminder schedule, hard-deadline handling and inactive-version checkpoint reporting. These do not all block backend design, but the affected user-facing flow must remain gated until resolved and tested.

## Historical design and implementation notes

**Historical material below:** Sections 1-9 describe the prior publication proposal and contain superseded behavior, including v1 staying active, employee-only publication, strict parent-date containment and an earlier phased evidence gate. They are not current contracts. Section 10 records slices chronologically; earlier statements can be superseded by later entries and by section 0 above.

## 1. Objectives and invariants

1. A semantic edit to an eligible ongoing Goal creates a reviewable definition under the same Goal ID.
2. Before publication, current Goal fields, criteria, milestones, assessment inputs and evidence eligibility still resolve to the existing operative context.
3. Explicit publication requires a nonblank employee reason, attestation of manager discussion, deterministic validation and the latest READY result for the exact proposed definition and validation context. It does not create manager approval or change lifecycle.
4. Initial Draft creation, validation, approval and activation retain their existing policy; a proposed edit never becomes an implicit lifecycle approval.
5. Immutable historical snapshots and prior assessment outcomes are preserved. Latest-created does not mean operative.
6. Publication, its applicable projections, immutable event and idempotent receipt commit together or not at all.
7. Concurrent edits, validation, criteria/milestone changes, lifecycle transitions, hierarchy changes and assessment completions cannot silently overwrite one another or publish stale context.
8. A semantic change to a Completed commitment uses the later replacement workflow, not in-place publication. Descoping and continuation themselves remain later phases.
9. Keep Jira REST, existing ownership and identity boundaries; no LLM/provider calls while domain locks are held.
10. Version-specific evidence applicability and new manager decisions are Phase 3 work. Phase 1 must not treat a prior approval as approval for a newly published definition.

## 3. Proposed logical and physical model

Names below describe a candidate additive design. The review should verify types, compatibility and migration ordering before implementation.

### 3.1 Explicit selection and content

| Existing/new concept | Proposed representation | Invariant |
|---|---|---|
| Current Goal | Retain `goals` and live material columns as a projection for compatible readers | Projection equals selected operative definition; old writers must not mutate it outside the protected publication path |
| Operative selection | Nullable `operative_goal_version_id` on Goal, with a same-Goal composite foreign key to `goal_versions` | At most one operative selection; never point to another Goal; null has explicit initial-Draft/legacy meaning |
| Candidate selection | Nullable proposal-head version ID plus optimistic proposal revision, or equivalent one-per-Goal proposal record | Candidate belongs to Goal; rejected/abandoned drafts do not replace current |
| Content history | Continue using immutable `goal_versions.content` with a versioned envelope schema | Snapshot includes all material Goal fields including organization, exact criterion membership/definitions, milestone definitions, source context and validation-relevant values |
| Lifecycle | Retain current Goal lifecycle | Definition publication and lifecycle activation remain separate |

Use JSON snapshots as immutable definition envelopes rather than inventing duplicate top-level Goal entities. Existing criteria and milestones remain execution/domain identities. Their *selected definition* and membership must be resolved from the operative envelope; draft modifications must not mutate their operative projection.

Each milestone definition snapshot should include its milestone ID, title, description, completion criteria, source and due date. Status/progress are execution state, not immutable definition. Each criterion snapshot should identify the exact criterion/version and definition plus approval context, not blindly select the latest revision. Determine how proposed criterion approval interacts with existing criterion approval policy before enabling a changed criterion; do not silently approve it through Goal publication.

For candidate preparation, hold candidate-specific definitions in the proposal envelope and avoid updating shared criterion/milestone records. On publication, apply only explicitly approved definition changes to compatible projections and preserve execution-state separation. If a changed milestone would make existing completion misleading, block or require a separately agreed workflow; do not transfer completion to a new meaning.

### 3.2 Publication event

Introduce append-only publication events with Goal ID, old/new version IDs, per-Goal sequence, authenticated actor, nonblank reason, employee manager-discussion attestation, validation run ID, source/plan provenance, and server-generated UTC event time. Enforce same-Goal version references, unique sequence and retained-history rules.

Do not store the employee attestation as manager approval. Resolve any manager context from the trusted identity/profile state and label it as context, not verification that the discussion occurred.

Event sequence establishes ordering for a Goal. The stored UTC event timestamp is recorded within the transaction, not a proven database commit timestamp. For time-based historical reads, specify a conservative visibility/cutover contract: do not advertise exact commit-time reconstruction merely from transaction-start time. Use committed event visibility and deterministic per-Goal ordering; ambiguous concurrent wall-clock boundaries must not produce invented precision.

### 3.3 Command receipt

Add a bounded command receipt keyed by authenticated owner, command kind and idempotency key, containing a canonical request hash and committed response identifiers. Same key/same payload returns the original authorized receipt, even after later publications. Same key/different payload conflicts.

Write the receipt in the same transaction as the mutation. Do not persist a success receipt before the transaction commits. For this synchronous phase, a separate persistent RUNNING state is unnecessary; asynchronous workers would need explicit lease/fencing semantics later.

### 3.4 Assessment context and evidence boundary

Bind new assessment runs/results to an exact Goal version and immutable input context, including exact criterion version, milestone definition and evidence capture/review state. Keep legacy runs explicitly unknown where the original inputs cannot be proven. Historical read must not recalculate with the current Goal or write staleness changes.

On publication, old assessments stay attached to their old definition. Current summaries for the new version return an explicit unassessed/pending outcome rather than copying prior progress.

**Release gate:** Goal-ID-scoped evidence mappings and mutable approval rows cannot safely prove approval for a new definition. Before Phase 3 provides target-version applicability, a newly published definition must not automatically use old approvals as current evidence. Preserve historical mapping/approval records and expose a clear `reapproval_required`/unavailable state; do not globally archive Evidence or fabricate rejection. Existing initial/new-Goal evidence workflows must retain their intended behavior. If existing assessment paths cannot enforce this safely, gate publication until Phase 3 rather than ship a misleading success.

### 3.5 Enforceable integrity

- Composite foreign keys enforce Goal/version ownership and exact validation/version association.
- Serialize version allocation with a Goal row lock and unique `(goal_id, version)`.
- Protect operative selection/projection consistency using a single protected domain transition plus database constraints/guards appropriate to the final design; do not rely only on UI.
- Permit an initial Draft or legacy-unknown state without declaring an unapproved version operative.
- Ensure immutable events/snapshots and their evidence context survive ordinary deletion. Review existing `ON DELETE CASCADE`, nested trigger exceptions and ORM cascades, including user deletion and administrative cleanup.
- Index Goal/version, Goal/event sequence and owner/command lookup. Index specific temporal/reporting queries once their exact access pattern is reviewed.
- Status transitions, proposal publication and current projection changes must share locking/optimistic concurrency rules.

Concrete SQL, constraint deferral, rollout privileges and writer guard mechanics must be reviewed against actual deployed schema and migration state. A trigger alone is not proof of correct actor authorization or historical reconstruction.

## 4. Domain and API flow

Illustrative contracts; [Phase 0](M6.6-Phase-0-Contracts-and-Readiness.md) is authoritative for payload/error expectations.

1. **Prepare:** verify ownership/eligibility and expected current/proposal revision; normalize safe whitespace-only no-ops; create an immutable complete candidate version. No Goal/criteria/milestone execution mutation.
2. **Validate:** deterministically validate exact candidate, then run semantic validation outside locks. Persist the result against candidate and captured context. A later candidate edit makes the old result ineligible for publication.
3. **Preview:** show candidate/current diff, date/parent impacts, exact validation, and historical/evidence implications. For parent-child date changes, require final graph containment; do not silently adjust children.
4. **Publish:** authenticate and check receipt; acquire hierarchy lock when needed, then stable ordered Goal/resource locks; re-read state; verify exact latest READY validation, reason, attestation and all review revisions; apply projection/selection and append event/receipt; commit once.
5. **Current read:** existing Goal identity resolves current operative definition and lifecycle, with proposal/eligibility clearly distinguished.
6. **History read:** resolve the actual published definition and recorded inputs. Never refresh sources or run summary staleness mutations as part of history.

New Drafts retain ordinary creation/approval/activation. Existing active/approved changes are explicit publication; there is no new approval row. `PUT /goals/{id}` must not silently mutate protected definitions. Reuse typed v1 errors and return explicit stale/validation/ownership conflicts.

**Scope constraint:** publication must block a parent change whose selected final graph has invalid date containment. Coordinated multi-Goal replanning and complete parent-version context are Phase 4; do not claim Phase 1 independently supports a coordinated date shift that requires multiple related Goal updates.

## 5. Concurrency and transaction design

Proposed lock order for commands touching hierarchy:

1. Begin READ COMMITTED transaction.
2. Acquire existing hierarchy advisory lock in its required separate statement.
3. Claim/check owner+kind+key receipt with a unique constraint.
4. Lock all affected Goal rows in deterministic ID order, then criterion/milestone rows and other referenced records in one documented order.
5. Recheck full reviewed membership/revisions and final validity.
6. Write selection, projection, event and receipt, then commit once.

Commands without hierarchy involvement use the same compatible resource order but need not acquire the global hierarchy lock. All conflicting existing writers must be refactored or explicitly blocked while the feature is enabled. Existing approval-first evidence writers and source refresh must be considered before introducing cross-resource locks; a lock-order document must cover *all* participating writers, not merely publication.

No nested helper may commit or roll back the coordinator's session. Existing Goal, criterion, milestone, hierarchy, assessment and OAuth helpers require transaction-neutral staging or clear separation from the command.

Assessment/validation jobs capture exact input fingerprints before external work. Before writing any current result, recheck current definition/eligibility. Preserve a late result as historical for its evaluated version or report supersession; never attach it to the newer context.

Server UTC publication timestamps are generated at the final write. Commit visibility and per-Goal sequence, not a client timestamp, determine committed history. Receipt is returned only after commit.

## 6. Backfill, cutover and compatibility

### Baseline inspection before migration

Obtain an explicitly identified, authorized target before examining actual Flyway state. A fresh disposable database does not establish a deployed baseline. Record migration versions/checksum status and aggregate anomaly counts without exposing credentials or unrelated data.

### Candidate migration strategy

1. Add nullable/backfillable metadata and new immutable event/receipt structures with a new additive migration. Never edit applied migrations.
2. Inventory Active/Approved/Completed/Archived/Draft records, live projection versus snapshots, approval/validation mismatches, missing milestone/evidence contexts and existing assessment provenance.
3. Capture a cutover baseline reflecting the actual live definition and current related definitions **as observed**, while marking prior effective periods/approval provenance unknown where not provable.
4. Do not substitute highest approved snapshot when it differs from live Goal values; do not invent approval, past effective dates or reviewed evidence.
5. Preserve old behavior through an explicitly labelled legacy compatibility path until an approved conversion. New publication commands always enforce strict READY/attestation.
6. Deploy compatible readers and writer protections first; disable old workers/instances that can mutate protected data before enabling candidate/publication behavior.
7. Validate constraints and reconciliation counts in a disposable upgrade fixture and against approved aggregate cutover checks. Keep failure explicit; do not silently repair ambiguous historical records.
8. Feature gate publication until version-aware criteria, milestone and assessment/evidence behavior are all safe. Roll back to a revision-aware release or disable the feature; old binaries are not assumed safe after new writes.

Distinguish a **cutover baseline** from a historical publication: it documents observed current state and uncertainty. It does not claim that a manager approved the captured definition or that it was operative before observation.

### Legacy APIs

- Preserve exact Goal ID reads.
- Allow normal Draft edits only within the reviewed initial lifecycle contract.
- Return an explicit actionable conflict for old direct edits of protected ongoing definitions; do not silently apply or report success.
- Audit legacy creation, hierarchy, criterion, milestone, evidence, assessment, delete, import and background paths identified in Phase 0.
- Keep identity in `myimpact-api`, Goal business logic in `myimpact-ai`.

## 7. UI behavior

- Goal detail distinguishes current definition, a proposed revision and history.
- Employee sees complete field/criterion/milestone/date impact, validation outcome, reason and manager-discussion attestation before publishing.
- Proposed or unvalidated content never appears as operative or automatically changes evidence eligibility.
- Clear pending/unassessed or evidence-reapproval-required state after publication; never display inherited progress as new achievement.
- Existing Goal ID/deep links remain valid; historical views identify the version/context.
- Stale conflicts preserve draft input and require explicit reload/review.
- UI controls mirror backend authorization and freeze constraints but are not the enforcement boundary.

## 10. Outcome

Phase 1 has started with an additive snapshot improvement: new Goal snapshots record organization identity and active milestone definitions without copying milestone execution state. Snapshot creation refreshes previously loaded criterion and milestone collections after flushing pending changes and copies nested definition data, so stale collections or later in-memory edits do not silently alter the captured context. Existing historical snapshots are not modified. Milestone changes alone do not yet create Goal snapshots, and current criterion selection, operative selection, proposal isolation and publication safeguards are not yet implemented. This initial work does not make the Phase 1 workflow safe or complete.

Targeted validation of the latest slices: 100 hierarchy, proposal, Goal version, criterion and validation unit tests and 65 PostgreSQL integration cases passed. A broader API-focused run was stopped after producing no output for more than two minutes; it did not produce a result.

With the user's authorization, the [operative-pointer migration](../../../myimpact-db/migrations/V20261111053000__add_goal_operative_version_pointer.sql) and [version-classification migration](../../../myimpact-db/migrations/V20261111060000__classify_goal_definition_versions.sql) were applied to the existing local PostgreSQL database and all 45 migrations validated. Existing Goals have null pointers; no historical version was guessed or backfilled. Existing snapshots are classified as `STANDARD`, and `PROPOSAL` snapshots are excluded from legacy latest-version lookups. The internal repository can resolve an explicitly selected version, but existing workflows still use latest-standard semantics. In particular, a selected `PROPOSAL` would not yet be used by those workflows: publication must remain disabled until all relevant readers and writers are migrated and evidence safeguards are enforced. The pointer does not by itself protect the live projection, validate publication or preserve history against deletion.

The subsequent proposal-head/receipt, baseline-observation and observed-version migrations were tested on disposable upgrades and applied to the same local database; all 48 migrations validated. They do not automatically select a baseline or expose a user workflow.

The version-allocation lock covers repository-mediated allocation in PostgreSQL READ COMMITTED transactions. Goal lifecycle/definition service writes and criterion service writes now acquire the Goal lock before their mutation; criteria generation calls the provider before locking and rejects a changed Goal, lifecycle or standard-version baseline. The lock does not prevent direct writers from bypassing the protocol or serialize all milestone, hierarchy, assessment and evidence changes. Coordinated cross-service lock ordering, optimistic conflict checks and atomic publication remain required. This draft does not claim Phase 1 is complete.

Milestone service creation, modification, archiving and deletion now also lock the Goal before writing. Milestone writers refresh previously loaded milestone state after acquiring that lock, so a concurrent archive is rechecked rather than overwritten. These changes do not create definition versions for milestone edits or protect direct SQL, hierarchy, assessment or evidence writers. PostgreSQL tests cover a blocked milestone creation and a stale update after archiving.

Criterion writers also refresh previously loaded criterion rows and revisions after obtaining the Goal lock. PostgreSQL tests cover a concurrent retirement and concurrent revision allocation, including a session that loaded stale criterion state before waiting.

An internal validation method checks ownership and validates the latest proposal by its exact immutable version ID. It retains a late result on the evaluated snapshot and reports supersession if a newer proposal appears. It uses the existing validation input and persistence service; it is not an API or publication authorization, and it does not yet verify all milestone, hierarchy, baseline or evidence context needed for publication. The later prepared-proposal checks described below add head and baseline rechecks, but complete publication-time rechecks and transaction safeguards are still required.

An internal baseline-comparison helper now compares a snapshot with the live Goal definition and the currently selected approved criterion versions, rather than assuming the latest criterion revision is operative. It reports incomplete or different snapshots and rejects invalid current criterion selections. A match does not prove historical Goal approval, select a baseline, cover hierarchy or evidence, or provide authorization and writer serialization. The comparison is used by the internal preparation slice below, but cutover and publication remain disabled.

An internal, transaction-neutral preparation slice stores immutable proposed title, description, planned-date and structured-field versions, a same-Goal proposal head, and an idempotency receipt. Structured fields are merged as a patch; deferral changes remain explicitly unsupported. It requires an explicitly selected matching `STANDARD` or `OBSERVED` baseline, an ongoing lifecycle, owner identity and exact proposal/relationship revisions, and rejects an invalid merged start/end range. Direct preparation does not mutate live definitions or select a baseline, and it has no API or UI. Other definition fields, criterion proposal changes, milestone additions/removals, parent/child date containment, full validation context, publication and reader cutover remain to be implemented. Receipt locking is PostgreSQL READ COMMITTED only; the transaction owner must roll back on failure and return the result only after committing. Existing Goal deletion can cascade this history, so retention is not yet guaranteed.

The preparation slice also accepts patches to existing milestone definitions in the proposal envelope only, preserving their IDs and source while leaving live definitions and execution status unchanged. It does not support adding or removing milestones. Both proposal-validation entry points reject a current prepared proposal if its milestone definitions differ from its baseline; the existing validator does not yet evaluate changed milestones or their relationship to completion. Returning the definitions to their baseline permits the existing validation path. This safeguard does not make validation complete or permit publication.

Internal prepared-proposal validation checks the persisted proposal head and matching baseline before and after the provider call. The existing independently committing method retains late results on the evaluated version and reports supersession. A separate internal transaction-neutral method evaluates without holding the Goal lock, then takes it, rechecks the proposal and baseline, and stages the run in a savepoint. It requires PostgreSQL READ COMMITTED; a failed recheck or staged write leaves no validation run, while the caller owns the outer transaction and must commit before reporting success or roll back the whole batch on failure. Existing pending session changes are flushed before the savepoint and are outside its rollback boundary. The Goal lock is held until the outer transaction ends, but only coordinates writers that follow the same protocol; callers must preserve wider hierarchy and idempotency lock ordering. Neither method captures all hierarchy/evidence context or substitutes for a publication-time recheck, and changed milestone definitions remain blocked.

An internal basic readiness check requires the selected run to be the latest `READY` result for the exact prepared proposal, with matching owner, validation input, current rule set and prompt version. It reruns deterministic checks at the current UTC date, so an overdue deferral cannot inherit an earlier READY result. The caller must hold the Goal lock; this helper does not acquire all required publication locks or validate hierarchy, evidence or history, and it does not authorize publication. Existing initial-lifecycle readiness continues using the same latest-result ordering.

An internal hierarchy date preview checks the proposed Goal dates against known dates on its immediate parent and eligible Draft, Approved and Active children. As confirmed by the user, missing planned dates are allowed and only known boundaries are compared; dates are never inferred or changed. Completed and archived children are excluded from required child-date checks. The preview acquires the hierarchy advisory lock before deterministically locking adjacent Goals, requires PostgreSQL READ COMMITTED and leaves transaction ownership with the caller. It reports conflicts only and is not yet a publication guard or API. Frozen Goals are not yet represented, so their exclusion must be added with the freeze workflow. A later coordinator must check the final selected graph under the correct lock order, rather than treating an earlier preview as authorization.

The internal prepared-proposal date preview reads the candidate's dates and then rechecks the exact head and matching baseline after the hierarchy and Goal locks are acquired. A concurrent replacement is rejected instead of returning a preview for a superseded candidate. This covers one candidate and its adjacent live Goals, not coordinated multi-Goal replanning or publication. For commands that also need idempotency, acquire the hierarchy lock and then the idempotency lock before the preview's Goal locks; never take the idempotency lock after them.

An authenticated employee can now prepare, review dates and validate a title/description/date proposal from the Goal detail page. The API derives ownership from the authenticated identity, uses optimistic revisions and retry receipts, and rejects a stale baseline; the page keeps unsaved edits when a newer revision is discovered. The live Goal remains unchanged by these actions. The page explicitly says publishing is unavailable; existing legacy edit and criterion/milestone paths are not yet protected, and this UI is not a completed edit-to-publication workflow. Publication remains disabled until reader/writer, history and evidence safeguards are implemented.

An internal one-time baseline observation can select the latest standard snapshot for an owned ongoing Goal when the complete snapshot matches the live projection and current approved criterion selections. Alternatively, when a prior snapshot is incomplete or differs, it can capture a new `OBSERVED` snapshot from the current live projection and record the exact latest standard source. Both paths record observation time with historical effectivity unknown and create no approval; they do not guess historical content. Existing latest-standard reads ignore the new `OBSERVED` snapshot. Preparation and validation recheck both the selected observed content and the recorded standard source. Neither operation is exposed or run as a backfill.

The internal combined observed-baseline and proposal command takes the proposal idempotency lock before the Goal lock and uses a savepoint so a failed preparation does not leave its observation staged. The caller owns the outer transaction, must respect that lock order, roll back the entire outer transaction if a larger batch fails, and only return success after commit. SQLAlchemy flushes previously pending session changes before creating the savepoint; those changes are outside its rollback boundary. An exact or safely recognized whitespace-only no-op creates no proposal version, but it can still create an `OBSERVED` baseline version and a receipt. Existing cascading deletion can still remove observations, and no operative readers or publication workflow are enabled.
