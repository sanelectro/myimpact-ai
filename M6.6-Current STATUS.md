# M6.6 Status — Goal Criteria and Evidence-Based Assessment

**Status date:** 31 October 2026  
**Overall status:** Core implementation is substantially in place, but M6.6 is **not complete or release-ready**. The main release blockers are human review of the evaluation dataset, approved quality thresholds, and final integrated validation.

This note summarizes the current state recorded in the [M6.6 milestone brief](./M6.6-README.md), [technical plan](./M6.6-TECHNICAL-PLAN.md), and [evaluation dataset status](./M6.6-EVALUATION-DATASET-STATUS.md). The broader milestone plan lists 24 October 2026 as its last known checkpoint; rerun validation against the current development environment before treating test results as current.

## Where we are

The core workflow has been implemented across criteria, assessment, and UI:

- Goal criteria can be proposed, versioned, reviewed, and approved.
- AI assessments are persisted with evidence references and lifecycle/history; progress aggregation is deterministic.
- Goal Detail and Goals use shared assessment summaries, with a bounded Analyze Goals action.
- User-triggered reanalysis refreshes authorized GitHub/Jira evidence, versions changed content, and reports partial connector failures.
- Focused coverage exercises assessment, evidence freshness/versioning, employee feedback, manager-review distinctions, stale/obsolete history, and reanalysis flows.
- Product and trust-boundary decisions for M6.6 are recorded in the milestone brief.

This is a substantial implementation, not a completion sign-off. Source refresh is bounded and does not guarantee complete change detection; provider result caps and query behavior can miss changes. Last-verified presentation and broader source-access/API edge coverage are also still open.

### Human-review workflow implementation

The first implementation slice for the human-review workstream is now in
place. Migration `V20261101080000__create_m66_human_review_workflow.sql`
persists review batches, immutable case assignments, independent reviews,
adjudications, and audit events. The domain service enforces two distinct
assigned reviewers, hides the first review from the second reviewer until
submission, records matching labels as `AGREED`, requires explicit
adjudication for disagreements, requires a third person to adjudicate, and
keeps the dataset `HUMAN_REVIEWED` gate fail-closed.

This is workflow infrastructure only. No real reviewer decisions,
identities, adjudications, or approval metadata have been created. API,
authorization-policy wiring, frontend screens, eligibility integration, and
manual review remain open.

## Pending work

### Release blockers

1. **Complete human review and adjudication of the benchmark.**
   - Write and agree on annotation guidance.
   - Have at least two reviewers independently label the cases and resolve disagreements.
   - Review the partial-rollout case first: its outcome varied between `IN_PROGRESS` and `NEEDS_REVIEW`.
   - Record real reviewer identities, dates, adjudication, rationale, and the exact approved dataset version. Do not mark the dataset reviewed until this work is done.

2. **Expand and version the evaluation dataset.**
   - The current starter set contains six cases. Add reviewed cases for temporal/stale evidence, measurable targets, milestone completion, weak or conflicting sources, missing measurements, attribution, and mixed relevant/irrelevant evidence.
   - Maintain a versioned holdout set that is not used to tune prompts or thresholds.

3. **Agree and approve numeric release thresholds.**
   - Confirm metric definitions and denominators with the team.
   - Set thresholds based on reviewed pilot results and product risk tolerance.
   - Record approvers, approval date, rationale, and values. All threshold values are currently null and approval is `NOT_APPROVED`.

4. **Run the approved evaluation and meet its gate.**
   - Declare the approved dataset, prompt, and model versions.
   - Produce complete, successful results for every required case/repeat slot.
   - Meet the approved metric thresholds. Current scores are exploratory only and cannot be used as a release pass.

5. **Complete and record integrated validation.**
   - Validate migrations, backend and frontend tests, API contracts, and Playwright flows together.
   - Confirm Goal Detail/Goals parity, owner isolation, manager-review distinctions, failure handling, assessment history, and that assessments do not change goal lifecycle.
   - Record commands, environment, results, and remaining limitations before sign-off.

### Remaining quality and UX work

- Close broader source-access and API edge cases; the technical plan also identifies query-load retry and source-access limitation states as open.
- Finish last-verified metadata and its UI presentation.
- Add claim-level review or another reliable method before treating the current unsupported-claim metric as factuality coverage. It is currently an outcome-level proxy.
- Investigate repeatability before release. The criterion-assessment exploratory
  run reports `0.5000`; the completed category-aware retry reports `0.5714`
  repeatability. The partial-rollout case still varies across repeats.
- Keep the bounded retrieval limitation visible: connector result caps and query semantics mean a refresh is not exhaustive source-change detection.

## Completion decision
